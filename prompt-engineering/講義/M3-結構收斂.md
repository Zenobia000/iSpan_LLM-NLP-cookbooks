## 1. 開場：這一層要收回什麼控制權？

**把「輸出長什麼樣」的決定權，從模型的自由發揮收回到你定義的 schema 裡。**

M2 讓你把意圖收斂成一份 spec 契約，其中「Output format」那一欄寫了你要的結構。但寫在 prompt 裡的「請用 JSON」只是一句**請求**:模型可能照辦，也可能包一層 Markdown code fence、多講兩句解釋、漏一個欄位、把數字寫成字串。只要下游程式要 `json.loads()` 它，這些都是會炸掉 pipeline 的地雷。

這一層要做的是把「希望它是 JSON」升級成「**保證符合 schema**」。手段不是再多寫幾句叮嚀，而是把約束從 prompt 層搬到 API 層與型別層：用 Structured Outputs 讓模型在解碼時就只能產生合法結構，用 Pydantic 在邊界把文字驗證成型別化物件。這一層的產物是**可被程式信賴的資料**,它是 M4 檢索結果、M5 工具參數、M7 評估判準能直接吃進去的格式。

## 2. 學習目標

## 3. 核心概念脈絡

### 3.1 三層保證：從「請求」到「強制」

要求模型輸出結構，有三個層級的約束力，差別在於「約束發生在哪一層」：

| 層級 | 做法 | 約束力 | 適用 |
| :--- | :--- | :--- | :--- |
| **Prompt 要求** | 在 input 裡寫「請用 JSON 回傳」 | 無（只是文字請求） | demo、草稿、給人讀的輸出 |
| **JSON mode** | `text={"format": {"type": "json_object"}}` | 弱：保證**可解析** JSON，不保證欄位/型別/值域 | 快速串接、結構極簡單 |
| **Structured Outputs** | `client.responses.parse(text_format=Model)` | 強：保證符合 schema（欄位齊、型別對、enum 合法） | 需要型別化資料的所有正式場景 |

**關鍵差異在於約束的位置。** Prompt 要求是「拜託模型自律」；JSON mode 限制了解碼器只能吐合法 JSON，但欄位它說了算；Structured Outputs 把你的 schema 編譯進解碼過程，模型在生成每個 token 時就被限制只能走向合法結構ï¼這不是事後檢查，是事前約束。

> 心法：**不要用 prompt 防漏欄位，要用 schema 讓漏欄位變成不可能。**

2026 新專案的預設選擇是第三層。`responses.parse` 把 Pydantic model 自動轉成 schema，結果直接落在 `response.output_parsed`，已經是型別化物件，不需要你再手動 `json.loads()`。

### 3.2 Structured Outputs：用 Pydantic 拿型別化結果

把你要的結構寫成 Pydantic `BaseModel`，交給 `responses.parse`：

```
class User(BaseModel):
    name: str
    age: int
    is_subscriber: bool

response = client.responses.parse(model=..., input=[...], text_format=Users)
users = response.output_parsed          # 已是型別化物件，非字串
```

SDK 負責把 model 轉 JSON Schema、把回應解析回物件。你拿到的 `output_parsed` 已經保證每個欄位都在、型別都對。

> 不依賴 Pydantic 時（團隊非 Python、schema 來自 API contract），可直接傳 JSON Schema，但要注意 `strict=True` 只支援 schema 的子集合，且物件要加 `additionalProperties: False`、列出 `required`。

### 3.3 Function calling：把「結構」綁到「行動」

Structured Outputs 約束**模型回覆的資料格式**；function calling 約束**模型要你執行哪個外部動作、傳入什麼參數**。兩者都用 JSON Schema 描述結構，但目的不同：要回傳資料用前者，要查資料/改狀態/呼叫外部 API 用後者。

Function calling 是一個**三步協定**（嚴格說是「請求、執行、回填、再請求」的迴圈）：

| 步驟 | 做什麼 | 關鍵 API |
| :--- | :--- | :--- |
| **1. 請求附 tools** | 帶著工具 schema 發請求，讓模型決定要不要呼叫 | `responses.create(tools=[...])` |
| **2. 讀 function_call** | 從 `response.output` 找出 `type == "function_call"` 的 item，讀 `name` / `arguments` / `call_id` | `response.output` |
| **3. 執行並回填** | 用 `json.loads(arguments)` 解參數、執行本地函式、把結果以 `function_call_output`（帶 `call_id`）塞回 input | `function_call_output` |
| **4. 再請求** | 帶著回填後的 input 再發一次，讓模型根據工具結果產生最終答案 | `responses.create(...)` |

**Tool schema 是模型看見的 contract；真正會被執行的是你程式裡的 Python 函式。** 兩者要對得上。回填時 `call_id` 不可省，它告訴模型「這個結果對應哪一次呼叫」。

實務上會把多個函式放進 registry，由 `function_call.name` 路由到對應函式ï¼這就是 agent executor / graph node 的雛形（接 M5）。

### 3.4 鎖死工具參數：strict 與 tool_choice

兩個讓 function calling 從「大致可用」變「可信賴」的開關：

- **`strict=True` + `additionalProperties=False`**：前者要求模型嚴格遵循 schema，後者禁止模型自創 schema 以外的欄位。兩個一起，工具參數才真正鎖死。
- **`tool_choice`**：預設是 `auto`（模型自己判斷要不要呼叫工具，工具是可用能力，不是每次都得用）。當你在做表單填寫、參數擷取、必須走某個工具的流程時，用 `tool_choice` 指定強制呼叫特定工具。

> 分界線：若只是要模型回傳結構化**資料**，優先用 Structured Outputs，而不是「強制呼叫一個假工具來騙出參數」。function calling 留給真正有外部動作的場景。

### 3.5 結構化擷取：Pydantic 是 schema 的單一真實來源

把非結構文字（財報逐字稿、書籍描述）變成型別化資料，核心是讓 **Pydantic model 同時當 schema 來源與驗證器**：

- **`Field(description=...)`**：欄位描述會進到 schema，是給模型的提示，讓它知道每個欄位該抓什麼。
- **`Literal[...]`**：把欄位限定在固定值域（enum），分類任務的值域就用它鎖住，模型無法自創類別。
- **巢狀結構**：欄位型別可以是另一個 `BaseModel`（如 `list[Speaker]`），複雜結構照樣表達。
- **`model_validate_json()`**：把模型輸出的 JSON 字串**驗證並轉成物件**。這是把不可控文字收斂成可信賴資料的最後一道閘。
- **`ValidationError`**：驗證失敗時拋出，用 `try/except` 捕捉，讓 pipeline 能對壞資料做重試或記錄，而不是直接崩。

> 加 CoT 的技巧：在 model 裡放一個 `reasoning: str` 欄位（放在分類結果欄位之前），模型會先寫推理再給結論，且因為是結構化的，拆開很乾淨。

### 3.6 應用整合：分類器 + 串流 + Gradio

把上面的工具組裝成一個有 UI 的分類客服機器人，會碰到兩個整合點：

- **Streaming delta 事件**：要邊生成邊顯示，用 `client.responses.create(stream=True)`，逐一接收事件，從 `response.output_text.delta` 累積文字後 `yield`。這讓 UI 不必等整段生完才顯示。
- **Gradio 6 `ChatInterface(type="messages")`**：對話介面用 `type="messages"`，此時 `history` 直接是 `[{"role": ..., "content": ...}, ...]` 的 dict 串列，可直接拼進 `input`。

> 心法：**純 prompt 分類仍可能不穩，要穩定值域與格式，回到 function calling / Structured Outputs。** 先把問題分類成結構化的 category，再路由到對應工具或知識庫，效果通常優於讓模型一路自由發揮（銜接 M4 RAG、M5 agent）。

## 4. 程式碼導讀

> 指向 `03-structured-output/` 各 notebook，僅列關鍵 pattern。

**`01-json-mode.ipynb`：三層保證**
- 三段對比：prompt-only（`responses.create(input="請用 JSON")`）→ JSON mode（`text={"format": {"type": "json_object"}}`）→ Structured Outputs（`client.responses.parse(text_format=Users)`）
- 觀察重點：只有第三層的 `response.output_parsed` 保證欄位齊、型別對；前兩層都要自己 `json.loads()` 還可能漏欄位
- JSON Schema 版：不用 Pydantic 時直接傳 schema，記得 `additionalProperties: False` + `required` + `strict=True`

**`02-function-calling-basics.ipynb`：三步協定**
- 步驟一：`responses.create(tools=[...])`，工具 schema 帶 `strict=True` + `additionalProperties=False`
- 步驟二：`[item for item in response.output if item.type == "function_call"]`，讀 `name` / `arguments` / `call_id`
- 步驟三：`json.loads(function_call.arguments)` 執行本地函式，把結果以 `{"type": "function_call_output", "call_id": ..., "output": ...}` 回填
- `tool_choice` 示範：`auto`（不需工具時模型直接答）vs 指定 `{"type": "function", "name": ...}` 強制呼叫

**`03-structured-extraction.ipynb`：Pydantic 驅動擷取**
- `class Report(BaseModel)` + `Field(description=...)`；`Report.model_json_schema()` 餵進 tools 的 `parameters`
- `Report.model_validate_json(arguments)` 把輸出驗證成物件；`Literal[...]` 鎖分類值域；`reasoning: str` 欄位做 CoT
- 巢狀：`list[Speaker]`；驗證失敗用 `except ValidationError` 捕捉

**`04-classification-gradio.ipynb`：接上真實 UI**
- 串流：`client.responses.create(stream=True)`，逐 `event.type == "response.output_text.delta"` 累積後 `yield`
- Gradio 6：`ChatInterface(fn, type="messages")`，`history` 為 dict 串列，直接拼進 `input`
- 流程：先做問題分類（結構化 category）→ 再路由到工具/知識庫

## 5. 練習與驗收

**練習**
1. 拿一段你現有的「請用 JSON」prompt，分別用三層保證各跑一次，記錄各層出現過哪些壞輸出（多包 fence、漏欄位、型別錯、enum 越界）。
2. 用 `responses.create(tools=...)` 走完 function calling 三步協定，呼叫一個本地函式並讓模型根據結果產生最終答案。
3. 用 Pydantic 定義一個含 `Literal` 值域與 `Field(description=...)` 的分類 model，用 `model_validate_json()` 驗證輸出，並用 `try/except ValidationError` 處理壞資料。

**驗收標準**
- 交出一個分類器：用 `client.responses.parse(text_format=Model)` + Pydantic，類別欄位以 `Literal[...]` 鎖死值域。
- 對一批輸入跑分類，輸出 **100% 通過 `model_validate_json()`**（無 `ValidationError`、無越界類別），這條直接成為 M7 的 eval。
- schema 即契約：別人不看你本人，只看你的 Pydantic model，就能知道輸出會長什麼樣、值域是什麼。

> 通過標準：你的輸出不再需要下游程式「防禦性解析」。如果接手的人還要寫一堆 `if "key" in data` 來防漏欄位，代表結構還沒收斂完成。真正收斂後，schema 本身就是保證。
