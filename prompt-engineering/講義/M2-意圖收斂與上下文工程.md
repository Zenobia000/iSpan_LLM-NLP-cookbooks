## 1. 開場：這一層要收回什麼控制權？

**把「該做什麼」的詮釋權，從模型手裡收回到你寫的規格裡。**

M1 讓你看清 LLM 是機率機器：同一句話問三次，三種答案。多數人的直覺反應是「再多加幾句叮嚀」，於是 prompt 越寫越長、越寫越像保母交代。這條路是死路 —— 新一代模型嚴格遵循字面指令，你寫的每一句廢話都是它要服從的雜訊。

真正的解法是反方向的：**寫得更少，但把「意圖」寫到無可誤解**，再用「上下文工程」精準控制模型在每一步看得到什麼資訊。這一層的產物是一份**規格契約（spec）**——它是 M3 結構、M4 知識、M5 行為、M7 評估的共同起點。

## 2. 學習目標

2. 能區分 Business Rule 與 Model Rule，只保留前者
3. 能寫出七欄位的 spec 契約，並驗證它跨 OpenAI / Claude / Gemini 輸出結構一致
4. 能用「寫入 / 選擇 / 壓縮 / 隔離」四種手法管理 context window

## 3. 核心概念脈絡

### 3.1 減法革命：越強的模型，越不需要你指揮細節

新一代模型能力的提升，意味著「怎麼做」可以交還給它。你的工作是把「要什麼」講清楚。

**The Bitter Lesson 在 prompt 上的體現：** 任何「人為規定模型該怎麼想」的技巧，長期都會輸給「讓更聰明的模型自己決定怎麼想」。所以不要寫死推理步驟、不要規定它先做 A 再做 B。

**刪掉保母型 prompt。** 與其寫：

> 「第一步，先閱讀文章。第二步，找出三個重點。第三步，每個重點寫一句話。第四步，整理成條列……」

不如寫：

> 「用三條一句話的條列，摘要這篇文章的核心論點。」

模型知道怎麼摘要。你要給的是**結果的形狀**，不是過程的步驟。

**規則的斷捨離 —— 只留 Business Rule。** 把 prompt 裡的規則分兩類：

| 類別 | 定義 | 處置 |
| :--- | :--- | :--- |
| **Business Rule** | 不可妥協的硬約束：資安、金流、法遵、絕對禁止的行為 | **保留**，且要可驗證（最終落到 M5 guardrail / M7 eval） |
| **Model Rule** | 你「怕模型出錯」而加的叮嚀：「記得用繁體中文」「不要太囉嗦」 | **刪掉**。模型多半已會；真出錯，用 spec 的成功標準與評估去抓，而不是堆叮嚀 |

> 心法：**不要把 prompt 寫更長來防呆，要把「意圖」寫更清楚。**

### 3.2 把意圖寫精準：四元素 + CTCO

針對「嚴格遵循字面指令」的模型，一段有效的指令要精確定義四件事：

- **目的（Intent）**：這段輸出要達成什麼？
- **受眾（Audience）**：寫給誰看？決定語氣與深度
- **成功標準（Success Criteria）**：什麼樣才算對？（這條之後直接變 M7 的 eval）
- **絕對要避開的錯誤**：明確點名地雷，比模糊的「請小心」有效十倍

落到結構上用 **CTCO 框架**組織：

```
Context     ── 背景、前提、輸入資料從哪來
Task        ── 一句話的核心任務（祈使句）
Constraints ── 硬約束（Business Rule）+ 要避開的錯誤
Output      ── 輸出格式、長度、結構
```

（5W1H 留作補充 checklist，不當主架構。）

### 3.3 Few-shot 的正確定位：對齊格式，不是教推理

2026 的 few-shot **不是用來「教會模型推理」**——推理交給模型內建能力與 `reasoning_effort`。few-shot 的價值在**格式與風格對齊**：你給兩三個範例，模型就知道你要的輸出長什麼樣、語氣多正式。

做法是把示範放進對話訊息（assistant 角色），讓模型「看到自己過去這樣回答過」。

> 推理控制：對推理模型，用 API 參數 `reasoning_effort` / `verbosity`。對非推理模型，若要保留中間思考又不污染輸出，用 `<thinking>...</thinking>` 與 `<answer>...</answer>` XML 標籤隔離。

### 3.4 Prompt Chaining：人類掌舵的多階段工作流

當一個任務太大、一次做不好，不要叫模型「自己分解問題」，而是**你**把它切成可驗證的階段，每階段一個子目標，上一階段輸出餵下一階段。

經典例子是翻譯：**階段一粗翻 → 階段二潤飾**，品質明顯優於一次到位。每個階段都是一小片 spec，每個階段的輸出你都能檢查、能重試。

> 分界線：當「下一步該做什麼」由**你**決定 → 這是 chaining（M2）。當「下一步」要由**模型**決定 → 你需要的是 agent（M5）。

### 3.5 Spec 七欄位契約 —— 本層的高潮產物

把前面所有東西收斂成一份結構化文件。這份 spec 是你跟模型的契約，也是整個控制權階梯的共同起點：

| 欄位 | 內容 | 連到哪一層 |
| :--- | :--- | :--- |
| **Role** | 模型扮演的角色 | — |
| **Goal** | 一句話目標（= Intent） | — |
| **Inputs** | 輸入資料與來源 | M4 知識 |
| **Constraints** | Business Rule + 要避開的錯誤 | M5 guardrail |
| **Output format** | 結構/型別 | M3 結構 |
| **Success criteria** | 什麼算對 | M7 eval |
| **Examples** | few-shot 範例 | 格式對齊 |

**控制點上移**：你不再逐次微調詞彙，而是定義規格 + 驗證規格。同一份 spec 餵給 OpenAI、Claude、Gemini，三家應該都產生結構一致的輸出 —— 這是 spec 寫得夠好的檢驗。

**完整範例（客訴分類任務）：**

```
[Role]   你是電商客服系統的工單分類引擎。

[Goal]   把一則客訴文字，分類到正確的處理隊列。

[Inputs] customer_message: 顧客自由輸入的客訴內文（繁中，可能夾雜錯字）。

[Constraints]
  - (Business) category 只能是這五個之一：退款、物流、商品瑕疵、帳號、其他。
  - (Business) 涉及金流爭議者，priority 必為 "high"。
  - 要避開的錯誤：不要自創新類別；不要因為語氣激動就誤判為 high。

[Output format]  JSON：{ "category": <五選一>, "priority": "high"|"normal", "reason": <一句話> }

[Success criteria]
  - category 與人工標註一致（這條直接成為 M7 的 eval）。
  - 金流爭議 100% 標 high（硬指標）。

[Examples]
  輸入：「東西收到是壞的，要求退我錢」
  輸出：{"category":"商品瑕疵","priority":"high","reason":"瑕疵且涉及退款金流"}
```

注意這份 spec 裡**沒有**「請用繁體中文」「請仔細判斷」這類 Model Rule —— 全被刪掉了。留下的每一條都可驗證。

### 3.6 上下文工程（Context Engineering）

Spec 解決「指令」，上下文工程解決「模型在每一步看得到什麼」。Context window 是有限的預算，要當資源管理。四種手法：

| 手法 | 做什麼 | 典型場景 |
| :--- | :--- | :--- |
| **寫入（Write）** | 把關鍵資訊主動放進 context 或外部記憶 | 系統前提、agent.md（M5） |
| **選擇（Select）** | 只放進當下需要的片段 | RAG 檢索（M4）—— 不是塞全部，是檢索最相關 |
| **壓縮（Compress）** | 摘要、裁剪冗餘 | 長對話歷史的摘要式截斷（M5 chatbot） |
| **隔離（Isolate）** | 用結構/標籤分區，避免互相污染 | 把使用者輸入與系統指令用 delimiter / XML 分開（也是 M5 injection 防禦的基礎） |

> 洞察：上下文工程把 M2（指令）、M4（檢索）、M5（記憶與護欄）串成一條線 —— 它們都是在回答同一個問題「此刻該讓模型看到什麼」。

## 4. 程式碼導讀

> 指向 `02-intent-convergence/` 各 notebook，僅列關鍵 pattern。

**`01-prompt-basics.ipynb` —— CTCO 與減法**
- 用 `client.responses.create(input=[{"role":"system","content": ctco_prompt}, ...])` 對比「長叮嚀 prompt」vs「短 CTCO prompt」的輸出穩定度
- 觀察重點：刪掉 Model Rule 後輸出沒變差，反而更穩

**`02-few-shot-and-reasoning.ipynb` —— 對齊與推理控制**
- few-shot 以對話訊息形式注入（示範放 assistant 角色）
- 推理模型用 `reasoning={"effort": ...}`；非推理模型用 `<thinking>` / `<answer>` 標籤
- 驗證：同一組 few-shot 餵不同 provider，輸出格式應一致

**`03-prompt-chaining.ipynb` —— 多階段工作流**
- 多次 `responses.create()`，上一次的 `output_text` 當下一次的 user 輸入
- 翻譯案例：粗翻 → 潤飾兩階段

**`04-spec-writing.ipynb` —— 七欄位契約（本章高潮）**
- `build_spec(role, goal, inputs, constraints, output_format, success_criteria, examples)` 組裝 spec
- 同一 spec 分別餵 OpenAI（`responses.create`）、Claude（`messages.create`）、Gemini（`models.generate_content`），比對結構一致性

## 5. 練習與驗收

**練習**
1. 拿一段你現有的「長叮嚀 prompt」，刪到只剩 CTCO + Business Rule，比較前後輸出（用 M1 的多次取樣觀察穩定度）。
2. 把同一個任務拆成兩階段 chaining，證明品質優於一次到位。
3. 為一個真實任務（如：客訴分類、報告摘要）寫出完整七欄位 spec。

**驗收標準**
- 交出一份 spec：只含 Business Rule，明確定義四元素（Intent / Audience / Success / 避開的錯誤）
- 該 spec 餵 OpenAI / Claude / Gemini 三家，輸出**結構一致**（欄位齊、格式同）
- spec 的「Success criteria」欄位寫得夠具體，能直接拿去 M7 當 eval 的判準

> 通過標準：你的 spec 是一份「不看你本人也能照著驗收」的契約。如果別人拿去執行會問「這裡到底要什麼」，就還沒收斂完成。
