# M0　AI 典範轉移與原生工作者思維

> 控制權階梯的第零層：思維層。無對應 notebook，本章建立整套課程的世界觀。
> 全篇以 2026 現行做法描述。

---

## 0. 先看一個人怎麼讓 AI 自己跑一整晚

先別管「典範轉移」這四個字。我們從一個具體的下午說起。

Karpathy 想優化一段程式，但他沒有打開編輯器一行一行改。他做的事只有三件：第一，指定一個檔案，告訴 AI「你只能動這一個檔案，別的都不准碰」；第二，寫一個評估函式，告訴 AI「跑出來的東西好不好，看這個分數就知道」；第三，設一個時間預算，告訴 AI「你有八小時，到點就停」。交代完這三句話，他就去做別的事了。

八小時後他回來。在這三條邊界裡，AI 自己試了一輪又一輪，跑出了 **900 多個實驗版本**。Karpathy 沒有指揮其中任何一次嘗試，他只做了最後一件事：看著分數曲線，挑出最好的那一版。

請停下來看清楚這個畫面裡的分工。那 900 次具體的試錯，是 AI 做的。但「該優化什麼」（評估函式）、「能動哪裡」（檔案）、「跑到什麼時候停」（時間預算），全是人定的。**邊界由人劃，試錯由 AI 跑，判斷由人收。** 人沒有去做那 900 次苦工，但人從頭到尾都知道自己在要什麼、也看得懂結果好在哪。

這種工作方式——**人劃邊界、AI 大量試錯、人做最終判斷**——就是這一章要講的「典範轉移」。你的角色從「親手寫出答案的人」，變成「設計一個讓 AI 跑出對答案的環境的人」。這背後是一個正在發生的轉變，叫 **Software 3.0**（白話：用自然語言、而不是程式碼，當你指揮機器的主要介面）。

一句話收束，記住它，後面九個模組都在拆解它：**你可以外包你的思考（那 900 次嘗試），但不能外包你的理解（你劃的邊界、你做的判斷）。** 接下來的 §1 到 §3，就是把這句話一層一層展開成可操作的工程。

## 1. 開場：這一層要建立什麼思維？

**把你的角色，從「親自寫出答案的人」改成「設計讓 AI 跑出對的答案的環境的人」。**

過去十年，工程師的價值等於「手寫程式的能力」。2026 的現實是：模型已經能寫掉大部分程式碼，繼續比拚打字速度是死路。但這不代表工程師被取代，而是工作重心整個位移了。你不再逐行產出，而是**定義邊界、配置上下文、設計驗證迴圈**，讓 AI 在你劃出的範圍裡大量試錯，再由你判斷哪些結果可信。這一層不教任何 API，它要建立一個信念：**你可以外包你的思考，但不能外包你的理解（You can outsource your thinking, but you cannot outsource your understanding）。** 整套課程的後面八層，都是這句話的工程化展開。

## 3. 核心概念脈絡

### 3.1 Software 3.0：自然語言成為新的程式介面

軟體開發的介面變了。你不再只用程式語言對機器下指令，而是用**自然語言**寫 prompt、用**上下文工程**控制模型在每一步看得到什麼。程式碼仍然存在，但它越來越像是模型產出的「編譯結果」，你真正在編輯的是更上游的意圖與脈絡。

| 你在控制的東西 | 具體形式 | 本課對應 |
| :--- | :--- | :--- |
| **意圖** | 把模糊需求寫成精準、可驗證的規格契約 | M2 |
| **脈絡** | 動態決定模型此刻該看到哪些資訊 | M2 / M4 |
| **行為邊界** | 工具、記憶、護欄、迴圈 | M5 / M6 |
| **驗收標準** | 二元評估與回饋迴圈 | M7 |

> 心法：傳統工程師問「這段程式怎麼寫」；Software 3.0 工程師問「我要怎麼描述意圖、配置環境，讓模型穩定產出對的東西」。

### 3.2 巨齒狀智力（Jagged Intelligence）：能力不是平滑曲線

AI 的能力分布是**鋸齒狀**的，不是一條順滑上升的線。在「可驗證（verifiable）＋ 強化學習（RL）」覆蓋得到的領域（數學、程式碼、有明確對錯的任務），進步很快；但在常識、隱含脈絡、需要世界經驗的判斷上，它可能弱得離譜，甚至自信地說錯。

這條鋸齒線直接決定**任務分流**：

| 任務性質 | AI 表現 | 處置 |
| :--- | :--- | :--- |
| **可驗證、有明確對錯**（程式、數學、結構化擷取、有測試的工作） | 強，且越來越強 | 大膽外包給 AI，用驗證迴圈兜底 |
| **隱含脈絡、常識、價值判斷**（哪個方案該存在、什麼該刪、是否得體） | 弱且不穩 | 人類把關，AI 只當草稿與選項產生器 |

> 洞察：分辨一個任務落在鋸齒的哪一面，本身就是工程能力。把可驗證的丟給 AI，把需要理解的留給自己，這就是「外包思考、不外包理解」的操作定義。M1 會用實測讓你體感這條邊界。

### 3.3 AI 原生工作者的四層能力

當「怎麼做」的成本趨近於零，價值就轉移到四種能力上，它們恰好對應本課的四個關鍵模組：

| 能力 | 它在問什麼 | 對應模組 |
| :--- | :--- | :--- |
| **① 意圖精確度** | 我能不能把「要什麼」寫到無可誤解？ | M2 意圖收斂 |
| **② 判斷力** | 我能不能辨識 AI 哪裡錯了、哪裡在迎合我？ | M6 協作與防禦 |
| **③ 系統設計** | 我能不能配出讓 AI 穩定交付的工作環境？ | M5 Harness Engineering |
| **④ 持續校準** | 我能不能用量測證明系統真的變好了？ | M7 校準（EDD） |

這四層不是先後步驟，而是同一個工作者的四個面向。一個只會寫精準 prompt（①）卻不會校準（④）的人，永遠不知道自己的 prompt 到底有沒有效；一個會設計系統（③）卻沒有判斷力（②）的人，會放任 AI 的幻覺流進生產環境。

### 3.4 心態轉移：從「寫出答案」到「設計驗證環境」

這是整層最關鍵的一次翻轉。舊心態的成就感來自「我親手寫出了這段程式」；新心態的成就感來自「我設計的環境讓 AI 反覆跑出了對的程式，而我能證明它對」。

- **過去**：價值 = 產出的程式碼量
- **現在**：價值 = 你劃定的邊界品質 + 你的驗證迴圈強度 + 你對交付物的理解深度

當 AI 把「怎麼做」壓到趨近零成本，「做什麼」與「怎麼驗證」就變成最昂貴、最不可外包的部分。你的護城河不再是打字速度，而是**品味（taste）**：判斷什麼該存在、什麼該刪除，以及能否證明你真正理解你交付的系統。

### 3.5 模型演化視角：把 CoT / ToT / ReAct 當「化石」讀

你會在很多舊資料看到 CoT（Chain of Thought）、ToT（Tree of Thoughts）、ReAct 這些名詞。它們本質是**同一句話**：

> 「模型內部還不會自己想，所以我們把『想的過程』用 prompt 外掛到輸入裡。」

CoT 是手動要模型「一步步思考」；ToT 是手動展開多條思路再選；ReAct 是手動編排「思考→行動→觀察」的迴圈。這些都是在模型**還沒有內建推理能力**的年代，人類用 prompt 補上的外掛。

關鍵在於：隨著 RL 與 test-time compute 的進步，模型把這些能力**內化成了內建功能**。昨天還要你手寫一整段思維鏈，今天塌縮成一個 API 參數 `reasoning_effort`。

> **模型版本演進 = 把昨天還要你手動寫的 prompt 技巧，今天變成內建。**

| 概念 | 它當年解決的問題 | 今天它在哪裡 |
| :--- | :--- | :--- |
| **CoT** | 模型不會分步推理 | 內化為推理模型的內建思考 |
| **ToT** | 模型不會探索多條路徑 | 內化為較高的 `reasoning_effort` |
| **ReAct** | 模型不會自主用工具與迴圈 | 內化為 agent 的內建工具呼叫迴圈（M5） |

**這條演化線的教學定位：化石，不是工法。** 我們讀它，是為了看懂「今日模型的前世」、理解為何模型一直出新版，而**不是**要你回頭手寫這些技巧。要控制推理強度，你用的是 `reasoning_effort`（M2 會教），不是手刻一段「請你一步一步想」。把這些名詞當博物館裡的恐龍骨架：值得理解牠怎麼演化過來，但你不會牽一隻回家代步。

> 這與全課「不提舊寫法」的鐵則不衝突：被淘汰的是**寫法**，被保留的是**理解模型版本演進的敘事**。

### 3.6 案例：Karpathy 的 Auto-research（Co-pilot loop）

回到 §0 那個跑了八小時的下午，現在把它拆成可分析的結構。Karpathy 沒有手把手指揮模型每一步，而是給了它**三個乾淨的限制**，然後放手：

| 限制 | 內容 | 它在做什麼 |
| :--- | :--- | :--- |
| **一個檔案** | 只准動這一個檔案 | 鎖死變更範圍，結果可比對、可回滾 |
| **一個評估標準** | 一個明確的評估函式打分 | 把「好不好」變成可驗證的數字（鋸齒的「可驗證」那一面） |
| **一個時間預算** | 一個迴圈／時間上限 | 控成本、強制收斂，避免無限發散 |

結果：agent 在這三條邊界內**試錯，8 小時跑出 900+ 個實驗**。

這個案例具體展示了整層心法。人類沒有外包「理解」：是 Karpathy 定義了該優化什麼（評估標準）、在哪裡優化（檔案）、優化到何時停（預算）。人類只外包了「思考」，也就是那 900 次的具體嘗試。**邊界由人劃，試錯由 AI 跑，判斷由人收**，這正是你接下來九個模組要反覆練習的事。

## 4. 程式碼導讀

> M0 是世界觀建立章，**無對應 notebook**。後續每一層的 notebook 都是這一層信念的工程化展開。

如果你想在進入 M1 前先有一次手感，可以做一個**迷你 demo**，把 Karpathy 三限制縮到最小：

- **給模型一個檔案**：一段待優化的小程式（例如一個跑得很慢的函式）。
- **給一個評估函式**：一個能對產出打分的 `def evaluate(...) -> float`（例如跑得多快、測試過幾條）。
- **給一個迴圈上限**：`for i in range(N):`，每輪讓模型讀目前的檔案 + 上一輪的分數，產出新版本，再用 `evaluate` 打分，保留最佳。

```
迴圈骨架（概念，不是要你抄 API）：
  best = 初始版本
  for _ in range(預算上限):
      候選 = 讓模型根據 (目前檔案, 上一輪分數) 改寫
      分數 = evaluate(候選)
      if 分數 > best 的分數: best = 候選
  回傳 best
```

觀察重點不是「模型多會寫」，而是：**當你把邊界（檔案）、目標（評估函式）、預算（迴圈上限）三件事交代清楚，AI 的自主探索就變得可控、可比對、可收斂。** 把這三件事拿掉任一件，你立刻會看到它發散或亂跑，那正是後面每一層在補的洞。

## 5. 練習與驗收

**練習**

1. 挑一個你目前實際負責的系統或工作流，把所有任務攤開，逐一標註它落在巨齒的哪一面（可驗證 / 需人類把關），並寫一句理由。
2. 用四層能力框架自評：你目前最強、最弱的各是哪一層？對應到本課哪個模組要重點補。
3. 找一段你看過的 CoT / ToT / ReAct 教學，用一句話把它「翻譯」成「這是在補當年模型缺的哪個內建能力」，證明你把它當化石讀懂了。

**驗收標準**

- 能對著自己負責的系統，清楚說出**哪些該交給 AI、哪些要人類把關**，並給得出判斷依據（鋸齒的哪一面）。
- 能用一句話說清「外包思考」與「外包理解」的差別，並各舉一個自己工作中的例子。
- 能解釋「為什麼模型一直出新版」，並說明 `reasoning_effort` 取代了過去哪一類手寫技巧，而不誤以為現在還要手寫 CoT。

> 通過標準：你不再問「這題我要不要用 AI」，而是直接答得出「這題的可驗證程度多高、我要劃哪三條邊界、我用什麼來驗收它」。當任務分流變成你的反射動作，這一層就過了。

## 補充教材

> 本章無對應 notebook，這裡改以**講義內可直接取用的範本**呈現。兩份範本拿了就能用：第一份把巨齒狀智力變成一張可填的分流表，第二份把 Karpathy 三限制變成一個收斂任意探索型任務的填空模板。

### A. 任務分流工作表（Task Triage Worksheet）

把你手上的任務逐一丟進這張表，用**可驗證性**當分流的主軸：能不能寫程式判對錯，決定它落在巨齒的哪一面。錯誤代價則決定把關的鬆緊：可驗證但代價高的任務，仍要保留人類最後一道關。

填表規則：

- **是否可程式驗證對錯**：能寫出一個 `def check(output) -> bool` 就填「可」，只能靠人主觀感覺就填「不可」，介於兩者填「部分」。
- **錯誤代價**：出錯後要花多少成本收拾（低／中／高）。
- **結論**：可驗證 + 代價低 → **交 AI**；可驗證但代價高、或部分可驗證 → **協作**（AI 產出、人覆核）；不可驗證 + 靠判斷 → **人類把關**（AI 只當草稿與選項產生器）。

| 任務 | 是否可程式驗證對錯 | 錯誤代價 | 結論 |
| :--- | :--- | :--- | :--- |
| 把一批 PDF 發票擷取成結構化 JSON（有欄位規格可比對） | 可 | 低 | 交 AI |
| 為一支慢函式做效能改寫（有 benchmark + 單元測試） | 可 | 中 | 協作（測試自動把關，改動由人 merge） |
| 決定產品下一季要砍掉哪三個功能 | 不可 | 高 | 人類把關（AI 只列選項與利弊） |
| _（填入你的任務）_ |  |  |  |
| _（填入你的任務）_ |  |  |  |

> 心法：分流的判斷力本身不可外包。你能不能替一個任務寫出 `check()`，就是它能不能交給 AI 的操作定義。寫不出 `check()` 的任務，先別急著丟給模型，先想辦法把它的成功標準變得可驗證。

### B. Karpathy 式乾淨限制設定範本

任何探索型任務（調參、改寫、最佳化、找最好的某某），都可以收斂成**三條限制**再放手讓 AI 跑。把下面的填空模板填滿，你就有了一個「邊界由人劃、試錯由 AI 跑、判斷由人收」的迴圈。

填空模板：

```
任務一句話：____________________________________________

① 一個檔案（變更範圍）
   只准動：________________________________________
   （鎖死範圍，讓每次結果可比對、可回滾）

② 一個評估標準（成功的數字）
   評估函式：def evaluate(產出) -> float ＝ ______________
   分數越____（高／低）越好；目標門檻：______________
   （把「好不好」變成一個可驗證的數字）

③ 一個時間預算（停止條件）
   上限：____ 輪迴圈 ／ ____ 分鐘 ／ 連續 ____ 輪無進步就停
   （控成本、強制收斂，避免無限發散）

放手後人類只做三件事：看分數曲線、抽查最佳產出、決定收斂或再跑。
```

填好的範例（最佳化一支字串解析函式）：

```
任務一句話：讓 parse_log() 在不改變輸出的前提下跑得更快。

① 一個檔案（變更範圍）
   只准動：src/parser/parse_log.py（其餘檔案一律不准碰）

② 一個評估標準（成功的數字）
   評估函式：def evaluate(版本) -> float ＝ 在 10萬行樣本上的平均解析秒數
   分數越低越好；目標門檻：< 0.8 秒，且既有 42 條單元測試全綠
   （測試沒全綠的版本，evaluate 直接回傳 inf，視為淘汰）

③ 一個時間預算（停止條件）
   上限：50 輪迴圈，或連續 8 輪無進步就停

放手後人類只做三件事：看分數曲線、抽查最快版本的程式碼可讀性、決定 merge 哪一版。
```

> 洞察：這三條限制各鎖住一個會讓 AI 發散的變數：範圍、目標、成本。任缺一條，迴圈就會亂跑。能不能把一個模糊的「幫我弄好一點」翻譯成這三條可填的限制，就是你把探索交給 AI 的入場券。
