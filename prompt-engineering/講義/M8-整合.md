## 1. 開場：這一層要收回什麼控制權？

**把 M1–M7 散落的「單點控制」收成「一條端到端、可驗收的問答助理」。**

前七層你逐格從模型手裡收回控制權：M1 認清它是機率機器，M2 用 spec 鎖意圖，M3 用 schema 鎖結構，M4 用 RAG 鎖知識，M5 用 harness 鎖行為，M6 用跨模型互審鎖品質，M7 用二元評估鎖改進方向。每一層都能單獨示範，但**單點可控不等於系統可控**：真正的考驗是把它們串成一條資料流，且每個交接點都不漏。

這一層沒有新概念，它的價值在於**整合**：你要證明這些收斂手段能彼此咬合，組成一個「換掉任一模型也照樣跑、低信心會自己升級審查、整條流程可被評估集驗收」的系統。這份 capstone 是你交給課程的畢業答卷，也是 M9 把系統變產品的起點。

---

## 2. 學習目標

1. 能把 M1–M7 的收斂手段串成一條端到端的問答資料流，每個交接點都有把關
2. 能設計 Provider 抽象層，讓 OpenAI / Claude / Gemini 在同一介面下可熱切換
3. 能整合 RAG grounding、結構化輸出、moderation 護欄三道防線於同一請求路徑
4. 能設計「低信心 → 升級」的分流邏輯，並用對應 M1–M7 各層的 checklist 完成驗收

## 3. 核心概念脈絡

### 3.1 控制權階梯總回顧：每一層在 capstone 裡的角色

capstone 不是把七個 notebook 黏在一起，而是讓每一層各司其職、串成一條流水線。先把「每層收回什麼、在本專題扮演什麼」對齊一次：

| 模組 | 收回的控制權 | 在 capstone 的角色 |
| :--- | :--- | :--- |
| **M1 不可控性** | 認識問題 | 理解 temperature / 取樣為何不可控，決定哪裡要低溫、哪裡要信心訊號 |
| **M2 意圖收斂** | prompt → spec | 用一份 spec 定義助理該答什麼、答不出時該說什麼 |
| **M3 結構收斂** | 自由文字 → schema | 回傳 `{answer, citations, confidence}`，用 Pydantic 保證可解析 |
| **M4 知識收斂** | 記憶 → 檢索 | 把答案錨定在檢索到的文件，無命中就誠實說「不知道」 |
| **M5 Harness** | 對話 → 受控環境 | moderation 輸入護欄 + 間接 prompt injection 防禦 |
| **M6 協作與防禦** | 單體 → 多代理 | 低信心時呼叫另一家模型做跨模型互審 |
| **M7 校準（EDD）** | 感覺 → 量測 | 用評估集量 Factuality 與「不知道」率，記錄供回饋迴圈 |

> 心法：**capstone 的難度不在任一層，而在交接點。** 每兩層之間的介面（檢索結果怎麼進 prompt、信心分數怎麼觸發升級）才是真正考你工程品味的地方。

### 3.2 端到端資料流：一條請求要穿過幾道閘

把上表攤平成一條單向資料流，每一站都是一道可獨立驗證的閘門：

```
使用者問題
  → [Moderation 輸入護欄]                     (M5)
  → [RAG 檢索 top-k 文件]                      (M4)
  → [Provider 抽象層：OpenAI / Claude / Gemini] (M1, M6)
  → [結構化輸出 answer / citations / confidence] (M3)
  → [低信心 → 觸發跨模型互審 / 人工]            (M6, M7)
  → [記錄供回饋迴圈評估]                        (M7)
```

這條流的設計原則是**單向、可中斷、每站有預設安全值**：護欄擋下就直接回拒、檢索無命中就回「不知道」、信心過低就升級。任何一站失敗都不該讓整條流崩潰或靜默吐出錯答案，這正是 M6「Cascade failure：每個交接點設驗證閘門」的具體落地。

### 3.3 Provider 抽象層：讓模型成為可替換零件

capstone 要求三家模型可熱切換。重點不是「同時用三家」，而是**把模型隔離成可替換零件**：上層邏輯（護欄、檢索、信心分流）完全不該知道底下是哪一家。介面就一個函式 `generate(question, context, provider) -> Answer`，回傳同一個 Pydantic 型別，內部依 provider 走不同分支：

| Provider | 結構化輸出當前做法 | 回傳 |
| :--- | :--- | :--- |
| **OpenAI** | `client.responses.parse(text_format=Answer)` | 直接得到解析好的 `Answer` |
| **Claude** | `messages.create` 以 `tool_use` 強制工具 schema | 從 tool 參數取出欄位組 `Answer` |
| **Gemini** | `generate_content` 帶 `response_schema` | 從結構化回應組 `Answer` |

三條分支吐出**同一個** `Answer`，是抽象層成立的檢驗，這直接延續 M2「同一 spec 跨三家輸出結構一致」與 M3「保證符合 schema」。一旦抽象層立住，M6 的跨模型互審幾乎免費：互審不過是用 `provider="claude"` 再呼叫一次同個函式去查 `provider="openai"` 的答案。

> 洞察：**好的抽象層讓 M6 互審變成一行參數切換。** 如果你的互審要為每家模型重寫一套呼叫邏輯，代表抽象層沒做對。

### 3.4 三道防線整合：grounding × 結構化 × 護欄

這三件事在前面各自學過，capstone 要它們在**同一條請求路徑**上協同。三者責任互不重疊，缺一條就漏一類錯誤：

| 防線 | 擋住什麼 | 落點 |
| :--- | :--- | :--- |
| **Moderation 護欄** | 惡意 / 違規輸入；藏在文件裡的間接注入指令 | 進入檢索前先擋（M5） |
| **RAG grounding** | 幻覺、無據而答：強制答案錨定檢索片段，無命中回「不知道」 | 生成時把 context 餵進 prompt（M4） |
| **結構化輸出** | 格式飄移、無法解析：`{answer, citations, confidence}` 用 Pydantic 驗證 | 生成回傳即驗（M3） |

關鍵在順序與職責分離：**護欄在最前**（別讓髒輸入浪費後面算力），**grounding 決定答不答**，**結構化決定答案形狀**。`citations` 欄位是 grounding 與結構化的交會點：它強迫模型把「我根據哪幾段文件回答」寫成可驗證的欄位，而不是口頭聲稱。

### 3.5 低信心分流：把不確定性變成可執行的動作

M1 教過「機率輸出不可控」，capstone 的回答是：**不消滅不確定性，而是讓它觸發動作**。`confidence` 欄位不是裝飾，它是分流開關：

```
confidence ≥ 門檻   → 直接回傳
confidence <  門檻   → 升級：跨模型互審（M6）或轉人工
```

這把 M1 的「信心訊號」、M6 的「跨模型互審」、M7 的「人工審查 / 回饋」收斂成一條 if 分支。設計時兩件事要想清楚：**門檻怎麼定**（用 M7 評估集回測，找出 confidence 與實際正確率脫鉤的臨界點），以及**升級的成本上限**（互審多花一次模型呼叫，要不要設每日預算，呼應 M6 的迴圈上限控成本）。

> 分界線：**低信心走互審（M6）還是走人工（M9），取決於風險。** 低風險任務自動互審就好；高風險任務（金流、法遵）一律轉人工，這條線正是 M9「漸進式授權」的伏筆。

### 3.6 骨架留 TODO：可控性是練出來的，不是讀出來的

capstone notebook 刻意**只給骨架、把核心三段留成 `TODO`**：`retrieve()`（接 M4 向量庫）、`generate()` 的三家 provider 分支（接 M3 / M6）、低信心 fallback（接 M6）。這不是偷懶，是教學設計：整條流水線的「形狀」已經畫好（護欄、分流、記錄都接好了），缺的正是前面七層各自的核心實作。學員補完這三個 `TODO`，等於親手把七層串起來一次。

> 心法：**框架替你管好交接點，你只需把每層的零件塞回對的插槽。** 補不完，代表某一層你還沒真的學會，這正是 capstone 當驗收的用意。

## 4. 程式碼導讀

> 指向 `08-capstone/01-capstone-overview.ipynb`，僅列關鍵 pattern。

**資料模型：結構化輸出的契約（M3）**
- `Answer(BaseModel)` 定義三欄位：`answer: str` / `citations: list[str]` / `confidence: float`
- 三家 provider 不論底層怎麼呼叫，最終都組裝成這同一個型別

**`moderate()`：輸入護欄（M5）**
- `openai_client.moderations.create(model="omni-moderation-latest", input=text)`
- 回傳 `results[0].flagged`；被擋直接回拒，不進後續流程

**`retrieve()`：知識收斂（M4，留 TODO）**
- 接上你在 M4 建立的 chromadb collection，回傳 top-k 文件片段
- 無命中是合法狀態，要讓下游能據此回「不知道」

**`generate()`：Provider 抽象層（M1 / M3 / M6，留 TODO）**
- 依 `provider` 分流：OpenAI 用 `client.responses.parse(text_format=Answer)`；Claude 用 `tool_use`；Gemini 用 `response_schema`
- 三條分支回傳同一個 `Answer`，這是抽象層成立的檢驗

**`assistant()`：主流程編排**
- 順序固定：`moderate` → `retrieve` → `generate` → 低信心分流

**練習**

5. 設計 3 個間接 prompt injection 測試（惡意指令藏在文件裡），確認助理不被攻破。

**驗收標準：對應控制權階梯每一層的 checklist**

| 層 | 驗收項 | 通過條件 |
| :--- | :--- | :--- |
| **M1** | 信心訊號可用 | `confidence` 與實際正確率有相關，不是常數 |
| **M2** | spec 定義行為 | 答不出時依 spec 回「不知道」，行為可預期 |
| **M3** | 結構保證 | 三家 provider 輸出皆能被 Pydantic 解析，零格式錯誤 |
| **M4** | grounding | 答案有 `citations`；無檢索命中時正確回「不知道」率 ≥ 0.9 |
| **M5** | 護欄 | moderation 擋下違規輸入；3 個間接注入測試全數不越權 |
| **M6** | 跨模型互審 | 切換三家 provider 皆產生結構一致的輸出；低信心會觸發互審 |
| **M7** | 評估達標 | 評估集上 Factuality ≥ 0.8，且結果可記錄供回饋迴圈 |

> 通過標準：**整條流水線能換掉任一模型照樣跑、低信心會自己升級、整體被評估集驗收達標。** 如果你只能 demo 單一模型、信心分數沒人用、或拿不出評估數字，capstone 就還沒收斂完成，這正是「能測量它、約束它、驗證它」的最終檢驗。
