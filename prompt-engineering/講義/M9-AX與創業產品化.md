# M9　AX 與創業產品化

> 控制權階梯第九層（規模化層）。本章為策略章，無對應 notebook。
> 全篇以 2026 現行做法描述。

---

## 1. 開場：這一層要收回什麼控制權？

**把「系統能不能變成產品」的決定權，從技術手裡收回到你的判斷裡。**

M1 到 M8 你已經把一個不可控的模型，逐格收斂成可控、可驗收的系統。但「可控的系統」不等於「有護城河的產品」：前者是技術成就，後者是商業存活。當人人都能用同一批 API 拼出同樣的問答助理，技術本身不再是差異化。

這一層的轉折是：**競爭戰場從「人類使用者」擴張到「AI 使用者」。** 2026 的服務不再只給人看，還要能讓別人的 agent 調用、比較、優先選擇你。同時，當 AI 把「怎麼做」的成本壓到趨近零，真正昂貴、真正稀缺的，是「做什麼」的判斷。這一層的產物不是程式碼，是一份**能讓你的系統活下來的商業契約**：它建立在 M2 的 spec、M5 的 harness、M7 的評估之上，但回答的是完全不同的問題：別人為什麼選你，而且離不開你。

---

## 2. 學習目標

1. 能為 agent（而非只為人）設計服務介面，讓別人的 agent 在比較時優先選你
2. 能用漸進式授權的任務卡片，平衡自動化效率與風險
3. 能走完 Anthropic 創業四階段，從模糊想法收斂到有護城河的產品
4. 能說清楚在「怎麼做」趨近免費的時代，自己的不可替代價值是什麼

## 3. 核心概念脈絡

### 3.1 AX：把 agent 當成你的新使用者

過去二十年我們談 UX（User Experience）：介面要好看、流程要順手、給人類看。2026 出現了一個並列的新詞：**AX（Agent Experience Optimization）**。它的前提很直接：**未來呼叫你服務的，越來越多是別人的 agent，不是人的手指。**

一個使用者要訂餐、查保險、比機票，他不會自己逐家網站點，而是丟給他的 agent：「幫我搞定。」agent 會去比較多個服務，挑出「任務路徑最順」的那一個來執行。**你的服務在不在 agent 的選擇清單上、會不會被它優先選中，決定了你還有沒有生意。**

所以優化對象變了。不是把按鈕做得更大，而是把 API 與資料結構做得更讓 agent 願意調用：

| 優化維度 | 給人看（UX）的做法 | 給 agent 用（AX）的做法 |
| :--- | :--- | :--- |
| **入口** | 美觀的網頁、清晰的導覽 | 結構化、可被機器發現與調用的 API / MCP server |
| **資料** | 圖文排版、視覺層次 | 乾淨的 schema、明確的型別、可驗證的回傳結構 |
| **任務路徑** | 減少使用者點擊數 | 減少 agent 完成任務的步數與不確定性 |
| **信任訊號** | 品牌、評價、設計感 | 可預期的輸出、低失敗率、清楚的錯誤語意 |

> 心法：**把 agent 當成一個會挑剔、會比較、會記仇的新使用者。** 它不看你的設計感，只看你的任務路徑順不順。讓 agent 用得最省力的服務，會贏。

注意這跟前面幾層是連續的：M3 的結構收斂、M5 的 MCP 標準介面，原本是為了讓**你自己的**系統可控；到了 AX，同樣的能力變成讓**別人的 agent**願意接你：你之前打磨的 schema 與工具介面，現在成了對外的競爭資產。


### 3.2 漸進式授權：用任務卡片分配自動化的膽量

當你的系統有能力自動執行任務，第一個誘惑是「全自動」。這是個陷阱：高風險動作一旦自動出錯，代價遠大於它省下的時間。但「全部都要人類確認」又退回到手動，自動化等於白做。

正解是**漸進式授權**：把生活/業務雜事拆成一張張**任務卡片**，每張卡片按風險分配「能不能自動執行」。

| 風險層級 | 判準 | 授權方式 | 範例 |
| :--- | :--- | :--- | :--- |
| **低風險** | 可逆、低金額、影響範圍小 | **自動執行**，事後可查 log | 整理收件匣、標記郵件、產生草稿、查詢資訊 |
| **高風險** | 不可逆、涉及金流/對外溝通/法律 | **人類核准後**才執行 | 付款、寄出對外信件、刪除資料、簽署 |

設計的關鍵不在「要不要授權」，而在**畫好那條風險線**，並讓每張卡片的授權層級寫得明確、可驗證：這正是 M2 的 Business Rule 與 M5 的 guardrail 在產品層的延伸。授權矩陣寫好，自動化才敢放手；放手了，效率才真的兌現。

### 3.3 Anthropic 創業四階段 Playbook

把可控系統變成產品，不是一次性的發布，而是四個階段的收斂。每一階段都有它要回答的問題與要交出的產物。

| 階段 | 要回答的問題 | 核心動作 | 產物 |
| :--- | :--- | :--- | :--- |
| **Idea** | 這個痛點是真的嗎？ | 用 AI 快速驗證痛點 | **可驗證假設** |
| **MVP** | 我到底要做什麼、不做什麼？ | 寫 Scope Doc + 安全審查 | **Scope Doc** + 受控 MVP |
| **Launch** | 怎麼穩定地運轉？ | 建立系統化營運 SOP | Weekly Matrix Brief / Support Triage SOP |
| **Scale** | 為什麼別人離不開我？ | 沉澱護城河 | 深度 / 專有資料 / 工作流綁定 |

**Idea：把模糊想法變成可驗證假設。** 不要愛上自己的點子。用 AI 當低成本的驗證引擎：快速做使用者訪談的分析、競品的拆解、市場訊號的整理，把「我覺得這很有用」收斂成一句**可被證偽**的假設，例如「X 類使用者每週為 Y 任務浪費 Z 小時，且願意付費換取自動化」。假設可驗證，才談得上 MVP。

**MVP：用 Scope Doc 防需求蔓延。** AI 讓「再加一個功能」變得幾乎免費，這正是危險所在：成本趨近零會誘發**需求蔓延（Scope Creep）**，MVP 越長越胖，永遠發不出去。對策是先寫一份 **Scope Doc**：明確列出這版**做什麼、不做什麼、成功長什麼樣**。它跟 M2 的 spec 同源：把意圖寫到無可誤解，只是這次約束的對象是你自己的衝動。MVP 也要做**安全審查**：你的服務一旦對外（尤其要被別人的 agent 調用），injection、資料外洩、誤動作都是真實風險，這是 M5 guardrail 在產品邊界的落地。

**Launch：把營運系統化。** 發布不是終點，是日常營運的起點。靠人記、靠救火撐不久，要把營運變成可重複的 SOP：

- **Weekly Matrix Brief**：固定週期的營運儀表，涵蓋關鍵指標、異常、待決策，一頁看完，不靠個人記憶。
- **Support Triage SOP**：客訴/問題進來時的分流標準流程（可直接接 M3 的分類器與 M5 的工單 agent）：什麼自動回、什麼升級人工、什麼是高優先。

**Scale：沉澱護城河。** 規模化的真正課題不是「服務更多人」，而是「為什麼別人換不掉你」。護城河有三種沉澱方向：

| 護城河類型 | 內涵 | 為什麼難以複製 |
| :--- | :--- | :--- |
| **深度（Depth）** | 在垂直領域做到別人做不到的精細 | 需要長期累積的領域理解，砸錢買不到 |
| **專有資料（Proprietary Data）** | 只有你手上才有的資料/回饋迴圈 | 別人沒有同樣的資料起點，模型再強也補不齊 |
| **工作流綁定（Workflow Lock-in）** | 嵌進使用者/agent 的日常路徑 | 切換成本高，已成為對方流程的一環 |

### 3.4 個人價值重塑：護城河是你的品味

把鏡頭從產品拉回到人。當 AI 把「怎麼做」的成本壓到趨近零，程式碼、文案、設計、分析都能瞬間產出，稀缺性整個翻轉：

> **怎麼做變便宜，做什麼變昂貴。**

當生產不再是瓶頸，瓶頸移到**判斷**。一萬個方案 AI 都能寫，但「該選哪一個、哪個該被砍掉」沒人能替你決定。這份判斷力有個名字：**品味（Taste）**。

品味不是玄學，它是兩種可被檢驗的能力：

| 品味的兩面 | 具體表現 | 怎麼證明你有 |
| :--- | :--- | :--- |
| **判斷什麼該存在、什麼該刪除** | 在無限多 AI 產出中，能挑出對的、砍掉冗餘的 | 你的 Scope Doc 砍得乾淨，產品沒有贅肉 |
| **能證明你真正理解你交付的系統** | 不是「跑得出來就好」，而是說得清為何這樣設計、邊界在哪、會在哪壞 | 系統出問題時你知道去哪查，而不是重跑碰運氣 |

這正是全課核心心法的終點：**你可以外包你的思考，但不能外包你的理解。** AI 替你思考（產出方案），但理解（判斷與設計）外包不掉，它就是你最後的護城河。一個能證明自己真正理解所交付系統的人，AI 越強，他越值錢。

## 4. 實作活動

> 本章無 notebook，改以兩份產品文件落地。兩份都是「不看你本人也能照著驗收」的契約。

**活動一：為自己的專案寫一份 Scope Doc**

選一個你想做的真實構想，產出一份 Scope Doc，至少含：

```
[一句話定位]   這個產品為「誰」解決「什麼痛點」。
[可驗證假設]   一句可被證偽的句子（X 類使用者 / Y 任務 / Z 成本或意願）。
[做什麼]       這版 MVP 明確包含的功能（盡量短）。
[不做什麼]     明確被排除、留到以後的功能（這欄最重要，防 Scope Creep）。
[成功長什麼樣] 可量測的成功判準（接得回 M7 的 eval）。
[安全審查]     對外/被 agent 調用時的風險與對應 guardrail。
```

要點：跟 M2 的 spec 一樣，把「不做什麼」寫到無可誤解，這一欄是 Scope Doc 對抗 AI 廉價生產誘惑的主防線。

**活動二：設計任務卡片授權矩陣**

把你產品（或你個人工作流）裡會被自動執行的動作，整理成任務卡片矩陣：

```
任務卡片 | 動作描述 | 可逆? | 風險層級 | 授權方式（自動 / 人類核准）| 對應 guardrail
```

要點：每張卡片的授權層級必須可驗證，別人看矩陣就知道哪些 agent 能自己做、哪些一定要人類點頭，而不需要問你。風險線畫在哪、為什麼畫在這，就是你品味的一次具體展示。

## 5. 練習與驗收

**練習**

1. 為你的構想走完 **Idea 階段**：用 AI 做痛點驗證（訪談分析 / 競品拆解 / 訊號整理），收斂出一句可被證偽的假設。
2. 為同一構想走完 **MVP 階段**：寫出完整 Scope Doc（含「不做什麼」與安全審查），並設計任務卡片授權矩陣。
3. 用一句話說明你這個產品的護城河屬於哪一型（深度 / 專有資料 / 工作流綁定），以及它為什麼難被複製。

**驗收標準**

- 交出一句**可驗證假設**：明確點出使用者族群、目標任務、可被證偽的成本或付費意願，不能是「我覺得很有用」這類無法檢驗的句子。
- 交出一份 **Scope Doc**：「做什麼」與「不做什麼」都明確，「成功長什麼樣」具體到能直接拿去當 M7 的 eval 判準，並含對外/被 agent 調用的安全審查。
- 交出一份**任務卡片授權矩陣**：每張卡片的風險層級與授權方式清楚，低風險自動、高風險人類核准的分界可驗證。

> 通過標準：把你的 Scope Doc 與授權矩陣交給別人，他能照著判斷「這版該做什麼、哪些動作可以放手自動」而不必回頭問你。如果別人會問「這到底要不要做」「這能不能自動」，代表你的判斷還沒收斂成契約；而判斷收斂成可交付的契約，正是這一層要證明的品味。
