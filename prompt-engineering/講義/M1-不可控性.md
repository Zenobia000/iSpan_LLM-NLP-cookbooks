## 0. 先連跑三次同一個 prompt，再談「不可控」

別急著理解「不可控性」這個詞。先做一件事：拿同一句問題，原封不動連問模型三次，看它回什麼。

```python
# 概念骨架（真正可跑版見 02-sampling-and-uncertainty）
# 同一個 prompt，原封不動連問三次
prompt = "幫我想一句鼓勵新手工程師的話"

for i in range(3):
    答案 = 問模型(prompt)          # 一字不改，連問三次
    print(f"第 {i+1} 次：{答案}")
```

跑下去，你看到的會像這樣（輸出為示意）：

```
第 1 次：每個資深工程師都曾經是看不懂錯誤訊息的菜鳥。
第 2 次：別怕寫爛 code，能跑起來再優化，永遠比完美的空白檔案強。
第 3 次：你今天卡住的問題，就是明天你能教別人的東西。
```

同一句話、同一個模型，三次三種答案。新手第一反應通常是：「是不是我 prompt 沒寫好？」**不是。** 把這個直覺先打掉。

看完現象，現在替它命名：這叫 **機率取樣**（白話：模型每次是「抽」一個答案，不是「算」出唯一答案）。模型內部對「下一個字」其實是一張機率分布，它每次從這張分布裡抽一個，所以你連問三次就抽到三種。這不是 bug，是生成模型的物理特性。

這也就是為什麼需要「不可控性」這一章：既然單次輸出天生會抖，你要學的不是寫出完美咒語，而是把這個會抖的東西**收斂成可控系統**——這正是整個控制權階梯的第一層。本章就是帶你親眼看見它怎麼抖、再交給你收斂它的第一組槓桿。

> 你會碰到的第一個英文詞是 **Responses API**（白話：各家把 LLM 包成的統一呼叫介面，你只要丟訊息、拿文字）。它就是上面那個「問模型」函式底下真正在做的事，§3.1 會拆開講。

## 1. 開場：這一層要收回什麼控制權？

**先收回「認知」這一格：承認 LLM 本質不可控，才有後面逐層收斂的動機。**

整個控制權階梯的起點，不是教你怎麼控制模型，而是讓你**親眼看見它不受控**。同一句 prompt 問三次，回三種答案；換一家廠商，能力邊界又長得不一樣。這不是 bug，是機率取樣的本質。

多數初學者卡在這裡：把不穩當成「prompt 沒寫好」，於是無止境地改咒語。本層要打掉這個錯覺：不穩是**生成模型的物理特性**，不是你的文字功力問題。理解「哪裡不可控、可控性槓桿在哪」，你才會在 M2 之後改用「規格 + 評估」這條真正能收斂的路，而不是繼續調咒語。

這一層的產物是一種**體感**：你能指著輸出說「這裡是取樣抖動」「這裡是巨齒狀能力邊界」「這段 thinking 我看不到所以有對齊風險」，並知道每一種不可控對應哪一根槓桿。

## 3. 核心概念脈絡

### 3.1 統一介面：把 LLM 當成一個函式呼叫

新專案的標準入口是 **Responses API**：`client.responses.create()`。把它理解成「一個吃訊息、吐文字的函式」，你要操作的只有四類東西：

| 旋鈕 | 作用 | 備註 |
| :--- | :--- | :--- |
| `input`（訊息陣列） | 對話內容，含 `role`（system / user / assistant）| 多輪對話就是往陣列裡疊訊息 |
| `instructions` | 系統層級的角色與規則設定 | 等同 system message 的定位 |
| `max_output_tokens` | 輸出長度上限 | 超過會被截斷，也直接影響計費 |
| 取樣參數 | `temperature` / `top_p` 等 | 見 3.2 |

> 心法：**API 參數就是可控性槓桿。** 你對模型的所有「控制」都從這幾個旋鈕來，沒有別的魔法。先認得旋鈕，才談得上收斂。

### 3.2 機率取樣：不穩的根源與三根槓桿

LLM 每一步都在一個機率分布上「抽」下一個 token。抽樣的形狀由三根槓桿決定：

| 槓桿 | 做什麼 | 調高的效果 |
| :--- | :--- | :--- |
| **temperature** | 縮放機率分布的尖銳度 | 越高越發散、越有創意；越低越聚焦、越穩定 |
| **top_p**（nucleus） | 只在累積機率前 p 的候選裡抽 | 控制候選池的「廣度」 |
| **top_k** | 只在機率最高的 k 個候選裡抽 | 同樣控制候選池（部分廠商用） |

**回到 §0 那個「連跑三次、三種答案」的現象，現在我們量化它：** 同一 prompt、`temperature=1.2` 連跑 10 次，你會數到好幾種相異答案；降到 `temperature=0`，答案趨於一致。**低溫穩定、高溫多樣**，但即使低溫也不保證逐 bit 完全 deterministic（Responses API 沒有 `seed`，硬體與後端排程仍有微抖動）。

> 別把「不確定」當成你 prompt 沒寫好。它是取樣機制的物理性質。你能做的是調槓桿 + 設計流程，不是寫出完美咒語。

### 3.3 可重現策略：把不可控收斂回可控

既然單次輸出不可信，工程上用**流程**換穩定，而不是寄望單次：

1. **固定模型 + 固定 prompt + 低溫**：把可控變因都鎖死，縮小抖動空間。
2. **多次取樣 + 評估器**：同一輸入跑多次，用一個**評估器**（規則、assertion、或另一個模型）挑出最可信的那個，或做多數決。這就是 M7「評估驅動」的雛形。
3. **用信心訊號做程式層篩選**：取 `logprobs`、或從機率分布算**熵（entropy）**當作信心指標：熵高代表模型沒把握，可以丟給人工或觸發重試。

> 這三步是整堂課的縮影：**單一模型輸出不可信 → 用流程與量測把它收斂成可信系統。** 後面每一層（結構、知識、harness、評估）都是這個邏輯的展開。

### 3.4 巨齒狀智力（Jagged Intelligence）的實證

AI 能力不是平滑曲線。在「可驗證 + 經 RL 訓練」的領域（數學、程式碼）表現很強，但跨到常識、隱含脈絡、需要世界模型的任務可能突然很弱。

本層的任務是把 M0 講過的這個概念**用實測打進體感**：拿同類任務看它表現穩定，再拿一個鄰近但需要常識的變體看它翻車。記住這條鋸齒邊界：它決定了**哪些任務交給 AI、哪些要人類把關**，也是後面所有「該不該信任這次輸出」判斷的底層直覺。

### 3.5 Token 經濟學

模型不看字、看 token。Context window 是有限預算，輸入輸出都按 token 計費。實務上用 `tiktoken.encoding_for_model()` 取得對應編碼（現行 GPT-5.x / o 系列多走 `o200k_base`）來估算長度與成本。

| 概念 | 意涵 |
| :--- | :--- |
| **Context window** | 單次請求能容納的 token 上限；爆掉會報錯 |
| **計費單位** | 輸入 + 輸出 token，長 prompt = 真金白銀 |
| **`max_output_tokens`** | 你對輸出長度（與成本）的硬性閘門 |

> 這條直接通到 M2 的「減法革命」：每多一句廢話都是 token，既花錢又是模型要服從的雜訊。

### 3.6 推理模型：推理強度與不透明的對齊風險

推理模型把「思考」內化成一個可調參數。各廠的旋鈕不同，但概念一致，都是**用算力換正確率**：

| 廠商 | 推理強度控制 | 取得思考內容 |
| :--- | :--- | :--- |
| **OpenAI**（o 系列） | `reasoning={"effort": "low"/"medium"/"high"}` | 思考過程不對外完整揭露 |
| **Claude** | `thinking={"type":"enabled", "budget_tokens": N}` | 回傳含 `thinking` 與 `text` 兩種 block |
| **Gemini** | `thinking_config=ThinkingConfig(thinking_budget=N, include_thoughts=True)` | `parts` 內含 thought 部分 |

> **對齊風險：** 你能控制「想多少」，但多數情況看不全「怎麼想的」。thinking 不透明，意味著模型可能用你不認可的路徑得到對的答案（或用看似合理的路徑得到錯的答案）。effort 越高、token 燒越多，強度是成本與正確率的取捨，不是免費的。

### 3.7 多模態：統一的輸入介面

文字、圖、檔案，2026 走**統一 `input` 陣列**：用 `input_text` / `input_image` / `input_file` 三種 part 型別組裝成一則訊息，丟進同一個 `responses.create()`。不再為不同模態切換 API。

| 模態 | 現行做法 |
| :--- | :--- |
| **圖 / 檔案理解** | `input` 陣列裡放 `input_image` / `input_file` part |
| **語音** | Realtime API（事件驅動串流，`realtime.connect()`）；TTS 與語音轉文字走 `*-tts` / `*-transcribe` 系列模型 |
| **生圖** | 原生多模態生圖（OpenAI `gpt-image-2`、Gemini `*-flash-image`），輸出 base64 影像 |

> 重點不是記 API 細節，是建立「**所有模態都收斂進同一個介面與同一套機率本質**」的認知：圖片描述一樣會抖、一樣有能力邊界。

### 3.8 跨廠商邊界：別把一家當成全貌

同一個任務，三家模型的可控性槓桿、安全機制、結構化能力不完全對齊。Gemini 透過 `google-genai`（`from google import genai`）提供統一介面，幾個關鍵差異點：

| Gemini 特性 | 作用 |
| :--- | :--- |
| `response_schema` + `response_mime_type="application/json"` | 強制輸出符合指定 schema（M3 結構收斂的跨廠對應） |
| `safety_settings`（`HarmCategory` + `HarmBlockThreshold`） | 可調的安全門檻，是一根你能控的可控性槓桿 |
| `finish_reason` | `STOP` = 正常結束；`SAFETY` = 被安全機制攔截，必檢查，否則會把「被攔截」誤當成「模型沒能力」 |

> 洞察：**不可控不只來自取樣，也來自廠商邊界。** 同一 prompt 在 A 家通、B 家被 safety 攔，是常態。認得各家的槓桿與終止原因，才不會把廠商行為誤判成模型能力。這條直接鋪墊 M2「同一 spec 跨三家輸出結構一致」的檢驗。

## 4. 程式碼導讀

> 指向 `01-uncontrollability/` 各 notebook，僅列關鍵 pattern。

**`01-openai-api-intro.ipynb`：統一介面與旋鈕**
- 入口：`client.responses.create(model=..., input=messages, temperature=..., max_output_tokens=...)`，取 `.output_text`
- `instructions` 當系統訊息；多輪對話 = 往 `input` 陣列疊 `role` 訊息
- Token 與計費：`tiktoken.encoding_for_model(model)`（現行多用 `o200k_base`）
- 觀察重點：同 prompt 切 `temperature=0` vs `1` 看輸出穩定度差異

**`02-sampling-and-uncertainty.ipynb`：取樣、一致性、信心訊號**
- 一致性實證：`ask_openai(prompt, temperature, runs=10)` 數相異答案數
- 三家取樣對照：OpenAI `responses.create(temperature=...)`、Claude `messages.create(temperature=...)`、Gemini `generate_content(config=GenerateContentConfig(candidate_count=3, temperature=...))`
- 信心訊號：`entropy(distribution)` 示範熵；實務改用 provider 當下支援的 `logprobs` 或評估器
- 收斂手法：低溫 + 多次取樣 + 評估器挑最可信

**`03-reasoning-thinking.ipynb`：推理強度與 thinking 不透明**
- OpenAI：`responses.create(..., reasoning={"effort": "low"/"medium"/"high"})`
- Claude：`messages.create(..., thinking={"type":"enabled","budget_tokens": N})`，遍歷 content block 取 `thinking` / `text`
- Gemini：`GenerateContentConfig(thinking_config=ThinkingConfig(thinking_budget=N, include_thoughts=True))`
- 觀察重點：effort / budget 越高，答對率與 token 成本同步上升；thinking 內容多半看不全 = 對齊風險

**`04-multimodal.ipynb`：統一 input 陣列**
- 組裝：`input` 陣列放 `{"type":"input_text"}` / `{"type":"input_image","image_url":...}` / `{"type":"input_file",...}`
- 語音：Realtime API `aclient.realtime.connect(model="gpt-realtime")` 事件驅動串流；TTS 走 `audio.speech` + `gpt-4o-mini-tts`
- 生圖：`gpt-image-2` 回傳 `b64_json`，base64 解碼存檔

**`05-gemini-model-boundaries.ipynb`：跨廠商邊界**
- 介面：`from google import genai` → `genai.Client()` → `client.models.generate_content(model=..., contents=..., config=...)`
- 結構化：`GenerateContentConfig(response_mime_type="application/json", response_schema=Model)`
- 安全槓桿：`safety_settings=[SafetySetting(category=HarmCategory.*, threshold=HarmBlockThreshold.*)]`
- 必檢查：`response.candidates[0].finish_reason`（`STOP` vs `SAFETY`）

## 5. 練習與驗收

**練習**
1. 取一個事實型問題，用 `ask_openai(prompt, temperature, runs=10)` 分別在 `temperature=0` 與 `temperature=1.2` 各跑十次，數出相異答案數，解釋差異從何而來。
2. 為同一個問題寫一個簡單評估器（規則或正則），把「低溫 + 多次取樣 + 評估器多數決」串起來，讓最終輸出穩定到單一答案。
3. 拿一個推理模型，比較 `effort` low / high 兩檔的答對率與 token 用量；觀察你能不能看到完整 thinking。
4. 同一 prompt 餵 OpenAI 與 Gemini，故意觸發 Gemini 的 safety，檢查 `finish_reason`，證明「被攔截 ≠ 沒能力」。

**驗收標準**
- 能用自己的話說明：**同一 prompt 多次輸出為何不同**（指到機率取樣 + temperature/top_p/top_k）。
- 交出一段可跑的程式：**低溫 + 多次取樣 + 評估器**，把一個原本會抖動的問題收斂成穩定輸出，並能展示收斂前後的相異答案數對比。
- 能指出至少一個**巨齒狀能力邊界**的實例（同類強、鄰近類弱），並說明它如何影響「該不該信任這次輸出」的判斷。

> 通過標準：你不再說「prompt 沒寫好所以不穩」，而是說「這裡是取樣抖動，我用低溫 + 評估器收斂它」。認知一旦從「調咒語」翻到「設計流程」，你就準備好進 M2 了。
