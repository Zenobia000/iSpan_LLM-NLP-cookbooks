## 1. 開場：這一層要收回什麼控制權？

**把「結果可不可信」的裁決權，從單一模型手裡收回到一套互相驗證的協作系統裡。**

到 M5 為止，你已經能為一個 agent 配出工具、脈絡、記憶、護欄與迴圈。但單體 agent 有個天花板：它的隨機性、幻覺與自我審查的過度自信，都關在同一顆模型裡，沒有任何外部視角能戳破。任務一長、agent 一多，問題不是消失，而是被放大 —— 一個 agent 的小錯沿著交接鏈傳下去，最後整個系統一起崩。

這一層要做的不是「再換一顆更強的模型」，而是**用結構抵銷單一模型的偏誤**：多個 agent 分工協作、不同廠商模型互相審查、在每個交接點設驗證閘門。產物是一套**可商用、高可信度的協作系統**——它把「我覺得這答案對」升級成「兩家模型互審後一致認定它對，且有 SOP 可重複」。

## 2. 學習目標

1. 能用 OpenAI Agents SDK 的 `Agent` / `Runner` / `@function_tool` / `handoffs` 組出多 agent 系統，並用 `trace` 觀測協作過程

## 3. 核心概念脈絡

### 3.1 多 agent 協作：用 Agents SDK 把分工結構化

當任務超過一個 agent 該負責的範圍，你需要的是**多個各司其職的 agent + 一套讓它們交棒的協定**，而不是把所有職責塞進一個巨型 prompt。OpenAI Agents SDK 把這件事收斂成四個基本件：

| 元件 | 角色 | 關鍵約束 |
| :--- | :--- | :--- |
| **`Agent`** | 一個有名字、指令、模型、工具的執行單元 | 一個 agent 只負責一件事，職責邊界清楚 |
| **`Runner`** | 驅動 agent 跑迴圈的執行器 | 用 `Runner.run(agent, input=...)`，多 agent 場景多為 `async` |
| **`@function_tool`** | 把 Python 函式變成 agent 可呼叫的工具 | **型別註記須與實際傳入值精確相符** —— SDK 依註記產生 schema，註記錯了模型就傳錯型別 |
| **`handoffs`** | 一個 agent 可以把控制權交給哪些 agent | 在 `Agent(handoffs=[...])` 宣告，形成可交接的拓撲 |
| **`trace`** | 把一整段協作包成可觀測的追蹤 | `with trace("..."):` 包住整個流程，事後可回放每一步 |

> 鐵則：`@function_tool` 的型別註記是契約，不是文件。`def process_refund(item_name: str)` 裡的 `str` 會直接變成模型看到的參數型別 —— 註記與實值不符，是多 agent 系統最常見的靜默故障源。

**三種協作模式，依「誰決定下一步」區分：**

| 模式 | 結構 | 下一步由誰決定 | 適用 |
| :--- | :--- | :--- | :--- |
| **Handoff（交接）** | A 把控制權整個交給 B，B 接手對話 | 當前 agent 自己判斷該交給誰 | 客服分流：triage agent 判斷是退款還是銷售，交給對應專員 |
| **Supervisor（督導）** | 一個主控每輪挑一個 sub-agent 來跑 | 主控 agent 每輪集中決策 | 需要中央協調、避免 sub-agent 亂跑的流程 |
| **Agents-as-tools** | 把其他 agent 包成 `@function_tool` 給主 agent 呼叫 | 主 agent 像呼叫工具一樣調度 | 翻譯編排：orchestrator 把各語言 agent 當工具，組合結果 |

三者不是越自動越好。**控制權上移的程度，要與任務可容忍的失控程度匹配** —— 客服分流用 handoff 很自然，但高風險流程更適合 supervisor 把每一步收在中央。

### 3.2 Deep search：受控檢索迴圈，不是放任搜尋

Deep search 是多 agent 協作的代表案例：給一個開放問題，agent 自己反覆搜尋、反思、補搜，直到湊齊答案。它的本質是一個**受控迴圈**，四個階段循環推進：

```
規劃（Plan）   ── 把大問題拆成子問題
搜尋（Search） ── 對每個子問題實際檢索（web_search 等工具）
反思（Reflect）── 檢查目前答案夠不夠，缺什麼
精化（Refine） ── 針對缺口再規劃、再搜尋
```

實作上有三個收斂要點：

- **`async` 並行**：子問題彼此獨立時，用 `asyncio.gather()` 把多個 `Runner.run()` 並行跑，把序列等待壓成一次等待。
- **Pseudo-tools 收斂行為**：把「產生子問題」「產生中間答案」也做成 `@function_tool`（如 `generate_sub_questions`、`generate_intermediate_answer`）。這些工具不一定真的去外部做事，目的是**逼模型把思考外顯成結構化呼叫**，讓迴圈行為可控、可觀測。
- **迴圈上限控成本**：`Runner.run(..., max_turns=30)`。預設值偏低（如 10），深搜要調高；但一定要設上限 —— 沒有上限的反思迴圈會無限燒 token。

> 分界線重申（接 M2）：當「下一步該搜什麼」由**模型**在迴圈裡決定 → 這是 agent（M6）；當每一步由**你**事先切好 → 那是 prompt chaining（M2）。Deep search 屬於前者，所以才需要 `max_turns` 這種安全閥。

### 3.3 四大失敗模式與防禦

多 agent / 長任務系統的崩潰，幾乎都落在這四類。每一類都有對應的工程防禦 —— 防禦不是「叮嚀模型小心」，而是在系統裡架可驗證的檢查點。

| 失敗模式 | 症狀 | 防禦手法 |
| :--- | :--- | :--- |
| **Silent failure（靜默失敗）** | 輸出表面合理、格式正確，底層事實是錯的；沒有任何報錯 | **Grounding check + 斷言**：把關鍵事實對回來源比對，用 `assert` 抓住「看起來對但對不上來源」的輸出 |
| **Spec drift（規格漂移）** | 長任務跑著跑著，逐漸偏離一開始的規格與目標 | **定期回貼 spec**：在迴圈中週期性把原始 spec 重新塞回 context，把 agent 拉回校準 |
| **Sycophancy（迎合）** | 模型迎合人類問題裡的錯誤前提，順著錯的往下推 | **挑戰前提**：在評估/審查環節刻意要求模型先質疑前提是否成立，而非直接作答 |
| **Cascade failure（連鎖崩潰）** | 一個 agent 的錯沿交接鏈傳遞，最後全系統一起垮 | **交接點驗證閘門**：每個 handoff 前後設驗證，上游輸出沒過閘門就不准傳給下游 |

> 心法：這四者的共通解法都是**「在錯誤傳播之前攔截它」**。Silent failure 攔在輸出處（grounding），Spec drift 攔在時間軸上（週期回貼），Sycophancy 攔在前提處（挑戰），Cascade 攔在交接處（閘門）。把驗證閘門想成多 agent 系統的 `assert`。

### 3.4 跨模型審核（Cross-Model Review）：用別家模型抵銷自家偏誤

單一模型審自己的輸出有個系統性偏差：**對自己的產出評分偏高，對別家的產出評分偏低**。讓同一顆模型既當作者又當審稿，等於球員兼裁判 —— 它的過度自信不會被任何外部視角戳破。解法是**讓不同廠商的模型互相審查**。

**Producer / Reviewer 分工：** 把「產出」與「審查」拆給不同模型，依各家強項配置：

| 角色 | 職責 | 取向 |
| :--- | :--- | :--- |
| **Producer** | 處理長任務、深度知識、生成草稿 | 偏向產能與廣度 |
| **Reviewer** | 嚴格除錯、挑事實錯誤與邏輯漏洞 | 偏向挑剔與精準 |

**架構：Writer → Reviewers → Synthesizer**

```
Writer       ── 一家模型產出草稿
Reviewers    ── 另外一或多家模型各自審查，輸出結構化意見
Synthesizer  ── 一家模型彙整所有審查意見，產出最終定稿
```

讓審查輸出走結構化格式（如 JSON），Synthesizer 才好機械化彙整，而不是讀一堆散文。

**量化一致性：embedding 餘弦相似度。** 把多份審查意見各自做 embedding，算兩兩餘弦相似度：

- 相似度高 → 多家模型看法一致，這份審查結論可信度高。
- 相似度低 → 模型之間有歧見，這正是需要人類介入的訊號。

這把「兩家模型是不是說同一件事」從主觀感覺變成一個可量測的數字。

> 終點：**把 Review 寫入 SOP。** 一次跨模型互審只是一次性動作；真正的產物是一份可重複執行的標準作業流程 —— 規定誰當 Producer、誰當 Reviewer、用什麼 prompt 審、一致性低於多少要升人工。這份 SOP 才是這一層的可交付資產，也是 M7 評估與 M8 整合的接口。

## 4. 程式碼導讀

> 指向 `06-multi-agent/` 各 notebook，僅列關鍵 pattern。四大失敗模式防禦與 Producer-Reviewer SOP 為**新增教材**（notebook 提供 code 骨架，講義補完防禦觀念與 SOP 文件化）。

**`01-openai-agents-sdk.ipynb` —— Agents SDK 與三種協作模式**
- 基本件：`from agents import Agent, Runner, function_tool, trace`
- 工具：`@function_tool` 裝飾函式，型別註記即 schema（`def process_refund(item_name: str)`）
- Handoff：`Agent(handoffs=[sales_agent, refunds_agent], ...)`，triage agent 分流
- Agents-as-tools：orchestrator 把各語言 agent 當工具編排
- 執行：`await Runner.run(current_agent, input=messages)`，整段包在 `with trace("..."):`

**`02-deep-search.ipynb` —— 受控檢索迴圈**
- 工具：`@function_tool async def perform_web_search(query)`、`fetch_webpage_text(url)`
- Pseudo-tools 收斂行為：`generate_sub_questions`、`generate_intermediate_answer`
- 迴圈上限：`await Runner.run(agent, input=user_query, max_turns=30)`（預設偏低，深搜要調高並設上限控成本）
- 並行版用 `asyncio.gather(*search_tasks)` 把多個子問題搜尋並行

**`03-cross-model-review.ipynb` —— 跨模型互審（本章高潮）**
- Writer：`claude_client.messages.create(model="claude-sonnet-4-6", ...)` 產草稿
- Reviewers（不同廠商）：
  - `openai_client.responses.create(model=..., text={"format":{"type":"json_object"}}, ...)`
  - `gemini_client.models.generate_content(model="gemini-2.5-flash", ...)`
- Synthesizer：再用一家模型 `messages.create(...)` 彙整審查意見成定稿
- 一致性量化：`embed()` 用 `text-embedding-3-small`，餘弦相似度 `a @ b / (norm(a)*norm(b))`

## 5. 練習與驗收

**練習**
1. 用 Agents SDK 組一個 handoff 系統（如客服 triage → 退款 / 銷售），用 `trace` 觀測一次完整交接，並指出交接點若沒設閘門會在哪裡發生 cascade failure。
2. 跑一次 deep search，刻意把 `max_turns` 設太低再設太高，觀察「答案不完整」與「成本失控」兩端，找出你的任務合理的迴圈上限。
3. 做一個 Producer → Reviewer 跨模型互審流程：一家模型寫草稿，另外兩家分別審查（輸出 JSON），算兩份審查的餘弦相似度，再用一家模型 synthesize 定稿。

**驗收標準**
- 交出一個 Writer → Reviewers → Synthesizer 流程，三個角色分屬不同廠商模型，審查輸出為結構化格式。
- 流程中量化一致性（餘弦相似度），並明定一致性低於某閾值時升人工審查。
- 交出一份**對應 SOP 文件**：寫清楚誰當 Producer / Reviewer、用什麼 prompt 審、四大失敗模式各對應哪個檢查點、升人工的觸發條件。

> 通過標準：你的互審流程是一份「換個人照 SOP 跑，也能得到同樣可信度」的可重複資產 —— 不是一次性的 demo，而是能寫進團隊作業手冊、接得上 M7 評估的協作協定。

### A. 四大失敗模式偵測檢核表

正文 3.3 講了四種模式的症狀與防禦方向；這張表把它變成「值班時逐列照查」的工具 —— 每一列告訴你**長什麼樣、在哪個位置抓、用什麼擋、哪一步能寫成程式自動跑**。

| 失敗模式 | 典型徵兆（人看得出） | 偵測點（在哪裡攔） | 攔截手段 | 可自動化的檢查 |
| :--- | :--- | :--- | :--- | :--- |
| **Silent failure** | 格式、語氣、結構都完美，但引用的數字 / 事實 / 連結對不上來源；模型沒報任何錯 | Producer 輸出處、寫入下游前 | 把每個關鍵事實對回原始來源逐條比對，對不上就擋 | `assert claim in source_spans`；引用 URL 回抓比對；數字與來源欄位做欄級 diff；無來源的斷言一律標記 |
| **Spec drift** | 跑到後段的產出，格式 / 範圍 / 口吻悄悄偏離最初 spec；單看當下那步看不出來 | 長迴圈每 N 輪、每次 handoff 前 | 週期性把原始 spec 重新塞回 context 校準；拿產出對 spec 逐欄位核對 | 每 N turn 自動重貼 spec；輸出對 spec schema 做 JSON Schema 驗證；關鍵欄位（語言 / 長度 / 類別集合）寫成斷言 |
| **Sycophancy** | 使用者問題自帶錯誤前提，模型不點破、順著錯的往下推，答得越詳細錯越深 | 評估 / 審查環節、回答生成前 | 強制 Reviewer 先質疑前提是否成立，再評內容；Producer prompt 內建「前提不成立就先反駁」 | 審查 prompt 固定加「先列出輸入中所有未驗證前提」欄位；偵測輸出是否無條件接受使用者宣稱（缺少 caveat 即標記） |
| **Cascade failure** | 上游一個小錯沿交接鏈放大，下游全錯，最後整條鏈一起垮 | 每個 handoff 的前後（交接閘門） | 上游輸出沒過閘門就不准傳給下游；閘門失敗即中止鏈、回退或升人工 | 每個 handoff 包驗證 wrapper：型別 / schema / 非空 / 值域檢查；閘門失敗計數，連續失敗觸發熔斷與告警 |

> 用法：把「偵測點」對到你系統的實際座標（哪個 function、哪次 `Runner.run` 之後），把「可自動化的檢查」那欄逐條落成測試或 runtime 斷言。沒落成程式的那幾格，就是你目前仍靠運氣的地方。

### B. Producer–Reviewer 跨模型互審 SOP 範本

以下整份可直接複製套用。`<尖括號>` 是你要替換的欄位。

```markdown
# 跨模型互審 SOP

## 1. 角色分工
| 角色 | 指派模型（廠商） | 職責 |
| :--- | :--- | :--- |
| Producer  | <例：Claude，Anthropic> | 產出草稿，承擔長任務與深度知識 |
| Reviewer A | <例：GPT，OpenAI> | 嚴格審查事實與邏輯，輸出結構化意見 |
| Reviewer B | <例：Gemini，Google> | 同上，提供第二個獨立視角 |
| Synthesizer | <例：Claude，Anthropic> | 彙整所有 Reviewer 意見，產出定稿 |

鐵則：Producer 與至少一個 Reviewer 必須是不同廠商模型（避免同源偏誤）。
Synthesizer 不得與唯一的 Reviewer 同一顆模型。

## 2. 觸發條件（符合任一即啟動互審）
- 產出將對外發布 / 進入生產 / 不可逆（金流、發信、寫 DB）。
- 涉及事實宣稱、數字、引用來源。
- 任務跨多個 agent 交接（cascade 風險）。
- 一次性低風險草稿（如內部腦力激盪）可豁免，但須在紀錄標註「未審」。

## 3. 審查 prompt 骨架（每個 Reviewer 共用）
```

```text
你是嚴格的審查者。先質疑前提，再評內容。只輸出 JSON，不要任何其他文字。

[待審內容]
<<<
{draft}
>>>

[原始 spec / 成功標準]
<<<
{spec}
>>>

審查步驟：
1. 列出待審內容中所有「未經驗證的前提」（對應 sycophancy 防禦）。
2. 逐條核對事實 / 數字 / 引用是否對得上來源（對應 silent failure）。
3. 核對是否偏離原始 spec 的格式與範圍（對應 spec drift）。

輸出格式（嚴格 JSON）：
{
  "verdict": "pass" | "fail",
  "confidence": <0.0 ~ 1.0>,
  "unverified_premises": [ "<前提1>", ... ],
  "issues": [
    { "severity": "high" | "medium" | "low",
      "category": "fact" | "logic" | "spec" | "premise",
      "location": "<指到哪一段 / 哪一句>",
      "detail": "<問題描述>",
      "fix": "<建議修法>" }
  ]
}
verdict 為 fail 的條件：存在任一 severity = high 的 issue。
```

```markdown
## 4. 一致性與分數閾值
- 一致性：對各 Reviewer 的 JSON 意見做 embedding，計算兩兩餘弦相似度，取平均 = consistency。
- 通過條件（全部滿足才放行）：
  - 所有 Reviewer 的 verdict 皆為 "pass"。
  - consistency ≥ <0.75>（依任務風險調整；越高風險閾值越嚴）。
  - 無任何 severity = "high" 的 issue。

## 5. 升人工規則（低於閾值的處置）
| 情況 | 處置 |
| :--- | :--- |
| 有任一 verdict = "fail" | Synthesizer 依 issues 修訂後重審一輪；連兩輪未過 → 升人工 |
| consistency < <0.75>（Reviewer 彼此歧見大） | 直接升人工 —— 模型之間沒共識，正是人類該介入的訊號 |
| 出現 severity = "high" issue | 升人工，且該草稿不得進生產 |
| 同一任務重審 ≥ <2> 輪仍未過 | 升人工並記錄為流程缺陷候選 |

## 6. 紀錄與追蹤欄位（每次互審留一筆）
| 欄位 | 說明 |
| :--- | :--- |
| review_id | 唯一識別碼 |
| timestamp | 互審時間 |
| task_ref | 對應任務 / spec 連結 |
| producer_model | Producer 用的模型與版本 |
| reviewer_models | 各 Reviewer 模型與版本 |
| verdicts | 各 Reviewer 的 verdict |
| consistency | 餘弦相似度平均值 |
| high_issue_count | severity=high 的 issue 數 |
| outcome | passed / revised / escalated |
| escalated_to | 若升人工，指派給誰 |
| final_draft_ref | 定稿位置 |
```

> 用法：第 1 節的模型指派與第 4、5 節的閾值是你要校準的旋鈕 —— 高風險任務把 consistency 閾值拉高、把豁免條件收緊。第 6 節的紀錄不是文書工作：它讓「哪類任務常升人工」「哪顆 Reviewer 最常挑出 high issue」變成可統計的數據，回頭優化 SOP 本身。
