## 1. 開場：這一層要收回什麼控制權？

**把「答案從哪來」的決定權，從模型的內部記憶收回到你給的資料上。**

M3 讓輸出有了型別保證，但型別對了不代表內容對。模型訓練資料有截止日、會把不知道的事編得煞有介事 —— 這就是幻覺。多數人的直覺反應是「在 prompt 裡多塞背景知識」或「換個更大的模型」。這兩條都是死路：前者塞不下、也分不清哪段才相關；後者再大的模型也不知道你公司昨天的內規。

真正的解法是換掉資訊來源：**讓模型回答前，先去外部資料裡檢索最相關的片段，把那幾段放進 context，再要求它只根據這些片段作答並附上引用。** 這就是 RAG（Retrieval-Augmented Generation）。它把「記憶」這個不可控的黑箱，換成「檢索」這個可查、可審、可引用的流程。

這一層也是 M2 上下文工程「**選擇（Select）**」手法的主戰場 —— RAG 的本質就是：不是把所有資料塞給模型，而是**動態挑出當下這一題最該看的那幾段**。檢索品質決定生成品質，這一層的工作幾乎全在「怎麼選得準」。

## 2. 學習目標

1. 能用 embedding + 餘弦相似度建出一條能跑的 vanilla RAG（解析 → 切塊 → 嵌入 → 檢索 → 帶 context 生成）

## 3. 核心概念脈絡

### 3.1 Embedding：把語意變成可計算的向量

RAG 的地基是 embedding —— 把一段文字映射成一個高維向量，讓「語意相近」變成「向量相近」。兩段文字的相關程度，用**餘弦相似度**（向量夾角的 cosine）量化：值越接近 1 越相似。

現行做法用 `text-embedding-3-*` 系列。關鍵在它支援 **`dimensions` 參數**：你可以把向量維度截短（例如 3072 → 1536 → 512），用儲存與檢索速度換一點精度。這不是舊模型的「固定維度」，而是同一個模型按需裁切。

向量本身看不懂，要驗證它有沒有學到語意，用兩個工具：**t-SNE** 把高維向量壓到 2D 視覺化，看相似主題有沒有聚在一起；**KMeans 分群 + LLM 自動貼標** —— 先把向量分成 k 群，再把每群的代表文字丟給 LLM 產生群組名稱。這條「無監督分群 + LLM 命名」是現行替人工標註省力的標準作法。

| 概念 | 做什麼 | 現行 API |
| :--- | :--- | :--- |
| **語意向量** | 文字 → 高維向量 | `client.embeddings.create(model="text-embedding-3-small", dimensions=...)` |
| **相似度量** | 量化兩段文字多接近 | 餘弦相似度（`cosine_similarity`） |
| **降維視覺化** | 驗證向量有無語意 | `TSNE(n_components=2)` |
| **自動分群貼標** | 替代人工標註 | `KMeans(n_clusters=k)` + LLM 命名每群 |

### 3.2 Vanilla RAG 五步：先把最笨但最清楚的版本跑通

不要一開始就上向量庫。先手刻一條五步流程，看清每一步在做什麼：

```
解析（Parse）   ── 從 PDF / 文件抽出純文字（pymupdf）
切塊（Chunk）   ── 切成有 token 上限的小段（按句子切，控 max_tokens）
嵌入（Embed）   ── 每塊算 embedding，存成向量陣列
檢索（Retrieve）── 算 query 向量與每塊的餘弦相似度，取 top-k
生成（Generate）── 把 top-k 塊當 context，要求模型只據此作答
```

最後一步是降幻覺的關鍵 —— 用**引用式 prompt**：要求模型先**逐字列出**它要引用的原文片段，再根據這些片段作答，並標上 `[1]`、`[2]` 來源編號。「先引用、再作答」這個順序強迫模型把答案綁在檢索結果上，沒檢索到就答不出來，比事後叫它「不要亂講」有效得多。

> 心法：**RAG 不是讓模型更聰明，是讓它不必用記憶硬撐。** 答得出來是因為你給了料，答不出來時它該說「資料裡沒有」。

### 3.3 相似度 ≠ 相關性：兩階段檢索

純 embedding 檢索快，但不準。問題在 embedding 是「把一整段壓成一個向量」的粗略表示 —— 兩段文字向量很近（高相似度），不代表後者真能回答前者的問題（高相關性）。一道題的正確答案，餘弦相似度可能還輸給一段「字面像、實際無關」的雜訊。

解法是**兩階段檢索**：

| 階段 | 角色 | 做法 | 現行工具 |
| :--- | :--- | :--- | :--- |
| **粗篩（Recall）** | 從上萬塊裡快速撈出候選 | embedding 餘弦相似度取 top-N（N 較大，如 50） | `text-embedding-3-*` |
| **精排（Precision）** | 從候選裡精準挑出真正相關 | reranker 把 (query, doc) 成對打分，取 top-k | Cohere `rerank-v3.5` / CrossEncoder `BAAI/bge-reranker-*` |

reranker 與 embedding 的差別：embedding 各自獨立編碼，reranker 是 **cross-encoder** —— 把 query 和候選文件**一起**餵進模型同時看，所以判斷相關性精準得多，代價是慢，因此只用在已粗篩過的少數候選上。粗篩保 recall、精排保 precision，兩者分工。

### 3.4 生產級向量庫：別再自己管向量陣列

手刻陣列檢索在幾百塊還行，上千上萬就崩。生產級用向量資料庫，現行標準是 **ChromaDB**：

- **`PersistentClient(path=...)`** —— 把索引落地存檔，重啟不必重算 embedding（開發試跑可用 `EphemeralClient()` 純記憶體）。
- **`get_or_create_collection()` + `collection.add(documents, embeddings, metadatas, ids)`** —— 建集合並寫入，每塊可附帶 `metadatas`（來源檔名、頁碼、日期等）。
- **`collection.query(query_embeddings=..., n_results=k)`** —— 向量檢索，且能用 metadata **過濾**（例如「只在 2026 年的文件裡找」）。metadata 過濾是純向量檢索給不了的：它把「語意相近」和「結構化條件」結合起來。

切塊不再手刻正則，用 **`langchain_text_splitters` 的 `RecursiveCharacterTextSplitter(chunk_size=..., chunk_overlap=...)`** —— 它按段落 → 句子 → 字元的層級遞迴切，並保留 `chunk_overlap` 讓相鄰塊有重疊，避免答案剛好被切在塊的邊界上而漏掉。

### 3.5 Dynamic few-shot：把 M2 的 few-shot 接上 M4 的檢索

M2 講過 few-shot 用來對齊格式。但範例該放哪幾個？靜態寫死幾個範例，對某些 query 根本不對題。**Dynamic few-shot** 把範例池當成一個可檢索的庫：對每一道進來的 query，**即時檢索出最相似的幾個範例**注入 prompt，而不是永遠用同一組。

只挑「最相似」會讓選出的範例彼此太像、覆蓋面窄。所以再加 **MMR（Maximal Marginal Relevance）** —— 在「跟 query 相關」和「彼此不重複」之間取平衡（`lambda_mult` 調比重），選出一組既切題又多樣的範例。這正是上下文工程「選擇」手法在 few-shot 上的具體應用：打通了 M2 的 few-shot 與 M4 的檢索。

### 3.6 Advanced RAG：vanilla 不夠時的五招

當 vanilla RAG 的檢索 recall 或 precision 撞牆，依瓶頸選招（不要全上，這違反簡潔原則）：

| 技巧 | 解決什麼 | 做法 |
| :--- | :--- | :--- |
| **Query Expansion** | query 用詞與文件用詞對不上 | LLM 把原問題改寫成數個變體，分別檢索後合併 |
| **HyDE** | 問題太短、語意稀薄 | LLM 先生成一個「假設的答案」，用**那段假答**的向量去檢索（假答跟真文件更像） |
| **Small-to-Big** | 小塊精準但 context 不完整 | 用小塊檢索命中，再透過 metadata（`parent_id`）擴展成所屬大塊餵給生成 |
| **Hybrid Search** | 純語意檢索漏掉關鍵字精確匹配 | BM25 關鍵字分數（`rank_bm25`）+ 向量分數，用 Reciprocal Rank Fusion 融合 |
| **Contextual Embeddings** | 切塊後脫離上下文、指代不清 | 嵌入前先用 LLM 替每塊補一句所屬文件的脈絡描述，再嵌入 |

通常的收尾仍是 3.3 的 reranker 精排。

### 3.7 PDF 解析三策略：依資料型態選，不要一招打天下

垃圾進、垃圾出 —— 檢索品質的上游是解析品質。PDF 依複雜度選策略：

| 策略 | 適用 | 做法 | 取捨 |
| :--- | :--- | :--- | :--- |
| **純文字** | 純文字、版面單純 | `pymupdf.open()` + `page.get_text()` | 快、免費，但丟失表格與版面 |
| **版面解析** | 有表格、多欄、結構 | `LlamaParse(result_type="markdown")` 轉成保留結構的 markdown | 準，需呼叫雲端服務 |
| **多模態讀圖** | 圖表、掃描件、複雜版面 | 把頁面當圖／檔，走 Responses API 原生 `input_file`（base64）讓模型直接「看」 | 最強，成本最高 |

多模態這條是現行新解：不再依賴 OCR 把圖硬轉成文字，而是把 PDF 直接交給多模態模型理解 —— `client.responses.create(input=[{... "type": "input_file", "file_data": "data:application/pdf;base64,..."}])`。

### 3.8 Agentic RAG：讓模型控制檢索，但你控制邊界

前面的 RAG 都是固定管線：一定檢索、檢索一次、然後生成。但有些 query 根本不必檢索（閒聊、常識），有些一次檢索不夠（複雜多跳問題）。**Agentic RAG** 把檢索的控制權交給模型，讓它自己決定要不要查、查幾次：

```
Route       ── 判斷這題該直接答，還是需要檢索
Plan        ── 複雜問題拆成子查詢
Retrieve    ── 執行檢索
Sufficiency ── 自評：檢索到的夠回答了嗎？（輸出 is_sufficient 布林）
Retry       ── 不夠 → 改寫 query 重查（設 max_steps 上限）
Grounding   ── 最終答案必須引用來源，做 grounding check 驗證沒亂講
```

關鍵原則：**可控性 > 自動化程度。** 不要做一個「全自主、無限重試」的 agent —— 那會失控、燒 token、難除錯。要的是**有閘門、有上限**的受控迴圈：每一步（Route / Sufficiency / Grounding）都是明確的檢查點，重試有 `max_steps` 硬上限。這呼應 M2 的分界線 —— 把「下一步該做什麼」的決定權交給模型，就進入了 agent 領域（接 M5 Harness），但邊界必須由你劃定。

> 這也是 RAG 與 M5 的接口：Agentic RAG 本質就是一個帶檢索工具的 agent，受 Harness 的工具迴圈與護欄約束。

### 3.9 路線補充：兩個要知道但別預設採用的方向

- **GraphRAG**：把知識建成實體關係圖再檢索，擅長「跨多份文件的全局性問題」（如「整個資料集的主題趨勢」）。代價是建圖貴、維護重 —— 確定有跨文件推理需求再上。
- **Long-context vs RAG 的取捨**：模型 context window 越來越大，「乾脆把整份文件塞進去」變得可行。但這不是萬靈丹：成本隨 token 線性漲、長 context 中段資訊易被忽略（lost in the middle）、且無法引用溯源。**經驗法則：** 資料量小且每次都要全看 → long-context；資料量大、要可引用、要省成本 → RAG。多數生產場景仍是 RAG。

## 4. 程式碼導讀

> 指向 `04-knowledge-rag/` 各 notebook，僅列關鍵 pattern。

**`01-embedding.ipynb` —— 語意向量地基**
- `client.embeddings.create(model="text-embedding-3-small", dimensions=...)` 取向量；餘弦相似度排序
- `TSNE(n_components=2)` 視覺化、`KMeans(n_clusters=k)` 分群後丟 LLM 自動貼標

**`02-vanilla-rag.ipynb` —— 手刻五步流程**
- `pymupdf.open()` + `page.get_text()` 解析；`tiktoken` 控切塊 token 上限
- `cosine_similarity()` 檢索 top-k；引用式 prompt（先逐字列引文、再作答、標 `[1]`）降幻覺

**`03-similarity-and-relevance.ipynb` —— 兩階段檢索**
- 對照 embedding 相似度 vs reranker 相關性（同一題分數會翻盤）
- `cohere.ClientV2().rerank(model="rerank-v3.5", top_n=k)` 或 `CrossEncoder("BAAI/bge-reranker-base").predict([[query, doc], ...])`

**`04-vector-db-rag.ipynb` —— 生產級向量庫**
- `chromadb.PersistentClient(path=...)` + `get_or_create_collection()` + `collection.add(documents, embeddings, metadatas, ids)`
- `collection.query(query_embeddings=..., n_results=k)` 搭 metadata 過濾；切塊用 `RecursiveCharacterTextSplitter(chunk_size, chunk_overlap)`

**`05-dynamic-few-shot.ipynb` —— 檢索式選範例**
- 範例池存進 collection，對每個 query `collection.query()` 撈最相似範例
- MMR（`maximal_marginal_relevance(..., lambda_mult=0.5)`）平衡相關與多樣，再注入 prompt

**`06-advanced-rag.ipynb` —— 進階檢索五招**
- Query Expansion / HyDE 用 LLM 生成查詢變體或假答後嵌入；多 query 一起 `collection.query()`
- Hybrid Search：`BM25Okapi` + 向量分數做 RRF 融合；收尾 `CrossEncoder` 精排；Small-to-Big 用 metadata `parent_id` 擴展

**`07-pdf-parsing.ipynb` —— 解析三策略**
- 純文字 `pymupdf`；版面 `LlamaParse(result_type="markdown")`
- 多模態 `client.responses.create(input=[{"type":"input_file","file_data":"data:application/pdf;base64,..."}])`

**`08-agentic-rag.ipynb` —— 受控檢索迴圈**
- `route_question()` → `rewrite_queries()` → `retrieve()` → `is_context_sufficient()` → 重試或作答 → grounding check
- 主迴圈 `agentic_rag(question, max_steps=3)`：每步是明確閘門、重試有硬上限

## 5. 練習與驗收

**練習**
1. 用 `02-vanilla-rag` 的五步流程對一份你自己的 PDF 建出 baseline RAG，觀察哪些問題答得出、哪些開始幻覺。
2. 在 baseline 上加一層 reranker（Cohere `rerank-v3.5` 或 `bge-reranker`），把檢索改成 embedding 粗篩 → reranker 精排兩階段。
3. 把生成 prompt 改成引用式（先逐字列引文、再作答、標來源編號），讓每個答案都能溯源。

**驗收標準**
- 交出一個**帶 reranker 與引用**的 RAG，與 vanilla 版跑同一組評估題。
- 用 M7 的 RAG 指標（如 Context Recall / Precision、Faithfulness、Answer Correctness）**量化證明**帶 reranker 版優於 vanilla 版 —— 不是「感覺比較好」，是分數有差。
- 每個答案都附引用來源；資料裡查不到的題，系統應回「資料中無相關內容」而非硬編答案。

> 通過標準：你交的不只是「能跑的 RAG」，是一份「能用數字證明它比上一版更好」的 RAG。如果你只能說「好像比較準」，這一層就還沒收斂完成 —— 量測是 M7 的工作，但 M4 的成果必須經得起 M7 的量測。
