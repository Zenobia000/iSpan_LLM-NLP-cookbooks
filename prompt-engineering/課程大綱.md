# AI 交互工程與系統設計（2026）課程大綱

> **AI Interaction Engineering** —— 帶學員從「寫提示詞的初學者」，升級為能指揮 AI 執行複雜系統任務的「AI 原生工作者」。
>
> 主軸：**把不可控的 LLM，逐層收斂成可控、可驗收、可商用的系統。**
> 全程以 2026 現行做法描述；多模型並陳（OpenAI / Claude / Gemini）；模型型號授課前以官方文件核對。

| :--- | :--- | :--- | :--- |

## M0　AI 典範轉移與原生工作者思維

**定位：** 建立 2026 軟體開發的新思維 —— 從「親自產出」轉變為「設計驗證環境」。

**學習目標**
- 理解 Software 3.0 對工程師角色的重塑
- 認識 AI 能力的非平滑本質，避免誤用
- 建立 AI 原生工作者的四層能力框架

**核心內容**
- **Software 3.0**：軟體開發從寫傳統 function，轉變為寫 prompt 與管理 context window；自然語言成為新的程式介面
- **巨齒狀智力（Jagged Intelligence）**：AI 能力不是平滑曲線。在「可驗證（verifiable）＋ 強化學習（RL）」的領域（數學、程式碼）進步極快，但常識、隱含脈絡可能極弱 —— 這決定了哪些任務該交給 AI、哪些要人類把關
- **AI 原生工作者的四層能力**：① 意圖精確度 ② 判斷力 ③ 系統設計 ④ 持續校準（恰好對應 M2 / M6 / M5 / M7）
- **心態轉移**：工程師的價值從「寫出答案」移到「設計讓 AI 跑出對的答案的環境與驗證迴圈」
- **模型演化視角（為何有不同版本）**：CoT / ToT / ReAct 這些「外掛思考」技巧，本質是同一句話 ——「模型內部還不會想，所以我們把想的過程用 prompt 外掛到輸入裡」。隨著 RL／test-time compute，模型把這些能力**內化成內建功能**，外掛便塌縮成模型的一個參數（`reasoning_effort`）。
  > **模型版本演進 = 把昨天還要你手動寫的 prompt 技巧，今天變成內建。**
  - 教學用途：這條演化線是用來**理解「為何模型一直出新版」**的最佳素材，不是要學員回頭手寫這些技巧。講授時定位為「化石」——看懂今日模型的前世，而非可使用的工法。

**案例**
- **Karpathy Auto-research（Co-pilot loop）**：用三個乾淨的限制 —— 一個檔案、一個評估標準、一個時間預算 —— 讓 agent 瘋狂試錯，8 小時跑出 900+ 實驗。示範「設定邊界讓 AI 自主探索」的威力
- **核心心法**：能外包思考，不能外包理解

**性質：** 全新概念章，需新撰講義（無對應 notebook）。建議作為開課第一堂的世界觀建立。

## M1　不可控性（uncontrollability）

**定位：** 建立「為何需要收斂」的動機。

**學習目標**
- 用 Responses API 把 LLM 當統一介面操作
- 理解輸出是機率取樣，掌握可控性槓桿
- 理解推理模型與多模態的能力邊界

**核心內容**
- **統一介面**：`client.responses.create()`；訊息角色、`instructions`、`max_output_tokens`
- **可控性槓桿**：`temperature` / `top_p` / `top_k`；低溫穩定、高溫多樣
- **可重現策略**：固定模型/prompt + 低溫 + 多次取樣 + 評估器；用 logprobs / 熵作為信心訊號做程式層篩選
- **巨齒狀智力的實證**：同類任務 AI 強、跨類任務 AI 弱 —— 對應 M0，用實測讓學員體感能力邊界
- **Token 經濟學**：`tiktoken.encoding_for_model()`、context window 與計費
- **推理模型**：`reasoning.effort`（OpenAI）/ `budget_tokens`（Claude）/ `thinking_budget`（Gemini）控制推理強度；thinking 不透明 = 對齊風險
- **多模態**：統一 `input` 陣列（`input_text` / `input_image` / `input_file`）；語音用 Realtime API 與 `*-tts` / `*-transcribe`；原生多模態生圖
- **跨廠商邊界**：Gemini `response_schema` + `safety_settings` + `finish_reason`；`google-genai` 統一介面

**notebook：** 01-openai-api-intro｜02-sampling-and-uncertainty｜03-reasoning-thinking｜04-multimodal｜05-gemini-model-boundaries

**驗收：** 能說明同一 prompt 多次輸出為何不同，並用低溫 + 評估器穩定它。

## M2　意圖收斂與上下文工程（intent-convergence + context engineering）★ 高潮

**定位：** 把人類模糊意圖收斂成規格契約；並動態管理模型在任務中所需的資訊。

**學習目標**
- 實踐提示詞減法革命與規則斷捨離
- 用 CTCO + spec 把意圖寫精準
- 掌握上下文工程的四種手法

**核心內容**

*減法革命（針對嚴格遵循字面指令的新一代模型）*
- **The Bitter Lesson**：放棄人為過度干預（死板思維鏈、保母型步驟），讓聰明模型自己決定怎麼做
- **刪除保母型提示詞**：停止「第一步做 A、第二步做 B」；模型越強越不需細節指揮，改結果導向
- **規則斷捨離**：刪掉怕模型出錯的 **Model Rule**，只保留不可妥協的 **Business Rule**（資安、金流、法遵）
- **優化心法**：不要把 prompt 寫更長來防呆，而是把「意圖」寫更清楚 —— 精確定義四元素：**目的（Intent）／受眾（Audience）／成功標準（Success Criteria）／絕對要避開的錯誤**

*意圖收斂的工具*
- **CTCO 框架**：Context → Task → Constraints → Output；5W1H 作補充 checklist
- **Few-shot 的定位**：用於格式 / 風格對齊，把示範放進 assistant 訊息
- **推理控制**：交給 API 參數（`reasoning_effort` / `verbosity`）；非推理模型用 `<thinking>` / `<answer>` XML 標籤隔離中間步驟
- **Prompt chaining**：人類掌舵的多階段工作流，每階段可驗證可重試
- **Spec 七欄位契約**：Role / Goal / Inputs / Constraints / Output / Success criteria / Examples；同一 spec 跨模型一致

*上下文工程（Context Engineering）*
- 定義：動態處理 LLM 在任務中所需資訊的藝術，四種手法 ——
  - **寫入（Write）**：把關鍵資訊寫進 context / 外部記憶
  - **選擇（Select）**：只放進當下需要的（接 M4 檢索）
  - **壓縮（Compress）**：摘要、裁剪冗餘（接長對話歷史管理）
  - **隔離（Isolate）**：用結構/標籤分區，避免互相污染
- Context window 是有限預算，要像管理資源一樣管理它

**notebook：** 01-prompt-basics｜02-few-shot-and-reasoning｜03-prompt-chaining｜04-spec-writing（上下文工程四法需補充新講義段落）

**驗收：** 交一份只含 Business Rule 的精簡 spec + 四元素定義，跨三家模型輸出結構一致。

## M3　結構收斂（structured-output）

**定位：** 讓輸出從「希望它是 JSON」變成「保證符合 schema」。

**核心內容**
- **三層保證**：prompt 要求 → JSON mode `text={"format":{"type":"json_object"}}` → **Structured Outputs `client.responses.parse(text_format=Model)`**
- **Function calling**：三步協定（請求附 tools → 讀 `response.output` 的 function_call → 回填 `function_call_output` → 再請求）；`strict=True` + `additionalProperties=False`；`tool_choice`
- **結構化擷取**：Pydantic `BaseModel` + `Field(description=...)`；`Literal[...]` 限值域；`model_validate_json()` + `ValidationError`
- **應用整合**：分類用 function calling / Structured Outputs；streaming delta 事件；Gradio 6 `ChatInterface(type="messages")`

**notebook：** 01-json-mode｜02-function-calling-basics｜03-structured-extraction｜04-classification-gradio

**驗收：** 用 `responses.parse` + Pydantic 完成一個保證 schema 的分類器。

## M4　知識收斂（knowledge-rag）

**定位：** 讓模型回答外部知識時有據可查、可引用。也是上下文工程「選擇」手法的主戰場。

**核心內容**
- **Embedding**：語意映射、餘弦相似度；`text-embedding-3-*` + `dimensions`；t-SNE 視覺化、K-means + LLM 自動貼標
- **Vanilla RAG 五步**：解析 → 切塊 → 嵌入 → 檢索 → 帶 context 生成；PDF 用 `pymupdf`；引用式 prompt 降幻覺
- **相似度 ≠ 相關性**：兩階段檢索 = embedding 粗篩 → reranker 精排（Cohere rerank / CrossEncoder `bge-reranker`）
- **生產級向量庫**：ChromaDB `PersistentClient()`；metadata 過濾；切塊用 `langchain_text_splitters`
- **Dynamic few-shot**：檢索動態挑最相似範例 + MMR 多樣性 —— 打通 M2 few-shot 與 M4 檢索
- **Advanced RAG**：Query Expansion、HyDE、Small-to-Big、Hybrid Search、Contextual Embeddings
- **PDF 解析三策略**：純文字 / LlamaParse 版面 / 多模態讀圖（Responses API 原生 `input_file`）
- **Agentic RAG**：Route → Plan → Retrieve → Sufficiency → Retry → Grounding；可控性 > 自動化程度
- **路線補充**：GraphRAG、Long-context 與 RAG 的取捨

**notebook：** 01-embedding｜02-vanilla-rag｜03-similarity-and-relevance｜04-vector-db-rag｜05-dynamic-few-shot｜06-advanced-rag｜07-pdf-parsing｜08-agentic-rag

**驗收：** 建一個帶 reranker 與引用的 RAG，並用 M7 指標證明它優於 vanilla 版。

## M5　Harness Engineering：打造 Agent 專屬工作環境

**定位：** 實踐「人類掌舵，Agent 執行（Human Steer, Agents Execute）」—— 不是調更好的 prompt，而是配置讓 AI 穩定交付的環境。

**學習目標**
- 用 Harness 五大架構設計 agent 工作環境
- 建立單一真實來源與工具標準介面
- 設計高容錯的 agent 系統架構

**核心內容**

*Harness 五大架構*
- **Tools**：為 AI 打造的工具（function calling 遞迴迴圈 + `max_depth`；parallel calls）
- **Context**：脈絡供給（接 M2 上下文工程 + M4 檢索）
- **Memory**：記憶（短期歷史壓縮、長期外部記憶）
- **Guardrails**：安全護欄（moderation `omni-moderation-latest`；prompt injection 防禦 = XML 分隔 + 指揮鏈 Chain of Command + 偵測模型；工具參數用 `json.loads()` 絕不 `eval()`）
- **Feedback loops**：驗證迴圈（agent 自動跑測試、看 log 報錯後自我修正）

*單一真實來源與標準介面*
- **`agent.md`（Single Source of Truth）**：把知識寫成 AI 可讀的文件，取代讓 AI「通靈」
- **MCP（Model Context Protocol）**：agent 對外接取工具的標準介面（原理 / server / client / Registry roadmap）
- **Skills**：橫跨 Context 與 Tools、封裝任務邏輯的「食譜」
- **Responses 內建工具**：`file_search` / `web_search`；`previous_response_id` 多輪狀態

*高容錯架構（參考 Anthropic Managed Agents）*
- 三層拆分：**Brain（無狀態決策）／ Hands（執行沙箱）／ Session（紀錄日誌）**
- 設計哲學：**從寵物到牲畜（From PETs to cattle）**—— agent 實例可拋棄、可重建，不依賴單一長壽實例

**案例**
- OpenAI 內部：agent 完成 100 萬行程式碼、1500 個 PR，人類 0 行手寫；工程師的工作是設計驗證環境與 feedback loop

**notebook：** 01-function-calling-agents｜03-langchain-agents（`create_agent` / LangGraph）｜04-function-calling-rag｜05-shop-guardrails｜06-prompt-injection｜07-plugin-tools｜08-chatbot｜09-responses-api（Harness 五大架構、agent.md、Brain/Hands/Session 需補新講義與範例）

**驗收：** 用 Harness 五要素配出一個能自動跑測試、報錯後自我修正的 agent。

## M6　協作與防禦：跨模型審核機制

**定位：** 解決 AI 隨機性、幻覺與多 agent 協作崩潰，建立可商用、高可信度的協作系統。

**學習目標**
- 用 Agents SDK 建多 agent 系統
- 辨識並防禦四大失敗模式
- 用跨模型互審抵銷單一模型偏誤

**核心內容**

*多 agent 協作*
- **OpenAI Agents SDK**：`Agent` / `Runner` / `@function_tool`（型別註記須與實值精確相符）/ `handoffs` / `trace`
- **協作模式**：handoff（交接）/ supervisor（每輪挑 agent）/ agents-as-tools
- **Deep search**：受控檢索迴圈（規劃 → 搜尋 → 反思 → 精化）；async；pseudo-tools 收斂行為、設迴圈上限控成本

*四大失敗模式防禦*
- **Silent failure**：表面對、底層錯 —— 用 grounding check 與斷言抓
- **Spec drift**：長任務逐漸偏離規格 —— 定期回貼 spec 校準
- **Sycophancy**：迎合人類的錯誤前提 —— 評估時刻意挑戰前提
- **Cascade failure**：多 agent 連鎖崩潰 —— 每個交接點設驗證閘門

*跨模型審核（Cross-Model Review）*
- 問題：模型對自己評分偏高、對別家偏低（自我審查過度自信）
- 解法：由不同廠商模型互相審查；**Producer / Reviewer 分工**（如 Producer 處理長任務與深度知識、Reviewer 負責嚴格除錯），主 agent 產出後呼叫另一模型審查
- 架構：Writer → Reviewers → Synthesizer；用 embedding 餘弦相似度量化一致性
- **把 Review 寫入 SOP**

**notebook：** 01-openai-agents-sdk｜02-deep-search｜03-cross-model-review（四大失敗模式、Producer/Reviewer SOP 需補新講義）

**驗收：** 做一個 Producer→Reviewer 跨模型互審流程，並寫出對應 SOP。

## M7　校準層：評估驅動開發（EDD）★ 課程靈魂

**定位：** 把「感覺有改善」變成「量測證明改善」。

**學習目標**
- 建立評估成熟度心智模型
- 用二元判斷打造 evals
- 跑回饋迴圈並判斷何時微調

**核心內容**
- **5-Level 評估成熟度**：外 → 入門 → 專業 → 自動化 → 自動最佳化（開篇心智框架）
- **評估驅動開發（EDD）**：放棄模糊的 1–10 分，改用明確的**二元判斷（對 / 錯）**打造 evals
- **三類評估**：有標準答案（程式 / assertion）/ 無標準答案（LLM-as-judge）/ 有參考資料（RAG）
- **RAG 評估**：合成評估資料（LLM 對 chunk 產生 Q&A）；No RAG vs RAG 對照；Braintrust + autoevals（RAGAS：Context Recall / Precision、Faithfulness、Answer Correctness）
- **回饋迴圈**：評分 → 失敗模式聚類 → 改進 → 同 dataset 再評估；改進優先序 = system prompt → few-shot → 檢索 → 微調
- **微調**：合成資料（chat JSONL）；SFT vs RAG vs **SFT+RAG（通常最佳）**
- **降低人類審核成本**：當 AI 產出變便宜、人類「理解」成本變高，放棄超長 Markdown，改用 **HTML 互動式介面**（卡片拖曳、並排比對）審核 AI 產出
- **自動最佳化（理論）**：gpt-prompt-engineer、DSPy、TextGrad

**notebook：** 01-rag-evaluation｜02-feedback-loop｜03-fine-tuning-synthetic-data（二元 evals、HTML 審核介面需補新講義）

**驗收：** 對某 prompt 跑一輪「二元評估 → 找失敗模式 → 改進 → 證明分數上升」。

## M9　AX 與創業產品化（Agent Experience + Startup Playbook）

**定位：** 把可控系統變成有護城河的產品 —— 理解 2026 產品競爭的新戰場。

**學習目標**
- 為 agent（而非只為人）設計體驗與介面
- 用漸進式授權平衡自動化與風險
- 實踐 AI 時代的創業四階段

**核心內容**

*AX（Agent Experience Optimization）*
- 未來的服務不只給人看，還要能讓 AI 調用
- 優化 API 與資料結構，確保 agent 在比較多個服務時，願意優先選你的任務路徑
- 思維：把 agent 當成你的新「使用者」

*漸進式授權*
- 把生活/業務雜事整理成**任務卡片**：低風險自動執行、高風險需人類核准

*Anthropic 創業四階段 Playbook*
- **Idea**：用 AI 驗證痛點，把模糊想法變成可驗證假設
- **MVP**：撰寫 **Scope Doc** 防範 AI 帶來的需求蔓延（Scope Creep），並做安全審查
- **Launch**：建立系統化營運（Weekly Matrix Brief、Support Triage SOP）
- **Scale**：沉澱護城河（積累深度、專有資料、工作流綁定）

*個人價值重塑*
- 當 AI 把「怎麼做」的成本壓到趨近零，「做什麼」的決策變得極其昂貴
- 護城河 = 你的**品味（Taste）**：判斷什麼該存在、什麼該刪除，以及能否證明你真正理解你交付的系統

**性質：** 全新策略章，需新撰講義（無對應 notebook）。建議作為結業堂，銜接學員自己的專案。

## 核心總結

2026 年最頂尖的開發者已意識到：**「原始智力」≠「智慧軟體系統」。** 單靠一個強大模型不夠。

本課程的價值在於：帶學員跳脫「不斷微調咒語」的盲區，轉向系統性的 **Harness Engineering** 與 **Context Engineering**，透過明確的邊界、工具、記憶與自動化評估迴圈（Evals），打造真正能在企業級環境穩定運作的 AI 應用 —— 並最終沉澱為個人與團隊的品味與護城河。

## 講義撰寫規格（每模組統一結構）

```
1. 開場：這一層要從模型手裡收回什麼控制權？（一句話）
2. 學習目標（3–4 條）
3. 核心概念脈絡（只描述當前做法）
4. 程式碼導讀（指向 notebook，貼關鍵 API pattern，不貼整段）
5. 練習 / 驗收標準（落到 M7 可評估的指標）
```

**鐵則：** 只描述當前最新做法，不提舊**寫法**（過時 API / 套件 / 咒語式 prompt），不做新舊對照，避免混淆。

**唯一例外（M0）：** 「模型演化視角」可講 CoT/ToT/ReAct 的**概念演化**，但定位是「解釋為何模型一直出新版」的化石，不是教學員回頭手寫這些工法 —— 這與「不提舊寫法」不衝突：淘汰的是**寫法**，保留的是**理解模型版本的敘事**。

**難用 notebook 呈現的概念，改以講義「補充教材」範本承載**（不另做 notebook）：M0 思維、M5 的 Harness 五架構 / agent.md / Brain-Hands-Session、M6 的四大失敗模式 / Producer-Reviewer SOP、M7 的二元 evals / HTML 審核介面、M9 AX 與創業 Playbook —— 皆已寫成各章末可直接取用的範本/檢核表/SOP。
